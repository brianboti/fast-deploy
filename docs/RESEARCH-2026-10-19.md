# Node.js web services, and what a data-bearing application needs: Fast Deploy 1.18.10 against research and practice

Written 2026-10-19 as a read-only review. Nothing in the code was changed; the plan it produces is in `docs/ROADMAP.md`
(Phases 18 and 19, decisions D41 to D47). The question asked was concrete: the platform must be able to deploy
`BetterCare_chatbot-main` ("Sophia", a Node.js chatbot for a hospital's SharePoint site), which it refused that morning
with "no Python code or dependency manifest". Two questions follow from it: how the platform takes a Node.js web service
as it is, with the same safety it gives Python; and what this particular application needs beyond Node, since it keeps
files, a database and a model on local disk and calls two model providers over the internet.

Method: the platform's code, documents and validation records were read (version 1.18.10, commit 45574f9; 675 tests pass;
27 tools), and the application's code, lockfile, tests and documents were read without running anything from it. Six
themed literature-and-practice searches then ran in parallel (Node.js on Cloud Run with Google's Node buildpacks, the
release line and the official images; building and running a Node container well; the npm supply chain of 2025 and 2026
and how to install, lock, audit and gate dependencies; how the platforms that deploy Node from source detect what to run,
read from their code; the pieces of this application that fight a stateless, egress-denied container; and which of the
pipeline's tools already handle Node), each returning only sources it had fetched or seen in search results, about 300 in
all. The load-bearing claims were then checked again directly (the Node release schedule, the npm changelog and command
pages, the bundled npm of each Node line, the Private Google Access rule), and section 9 marks each source as fetched,
seen in a search result only, or unverified. Prices were read from the **Cloud Billing Catalog API** on 2026-10-19
(effective that day) for `us-central1` or global, as in the review of 2026-10-16; Google's pricing pages still truncate
for an automated reader. Two limits: the application was read from a downloaded folder, not a repository, so nothing was
executed and its tests were not run; and no study measures "how many Node repositories deploy automatically", so the
figures in 4.2 are proxies from benchmarks that do not match the lab's repositories.

Acronyms: CNB (Cloud Native Buildpacks), FUSE (the user-space filesystem Cloud Run uses to mount a bucket), IAP
(Identity-Aware Proxy), LTS (long-term support, a Node.js release line), MAU (monthly active users), OSV (the open
vulnerability database Google runs; `MAL-` records are malicious packages), PGA (Private Google Access, the way a service
with no internet reaches Google's APIs), SBOM (software bill of materials), SSE (server-sent events, the streaming the
application uses for answers).

## 4. Question 1: a Node.js web service as it is

### 4.1 Which Node, and what the runtime gives for free

The schedule (nodejs/Release, read 2026-10-19 [F]): 20 reached end of life on 2026-04-30; 22 is in Maintenance (end of
life 2027-04-30; its last release, 22.23.3 of 2026-09-23, bundles npm 10.9.9); 24 is Active LTS (Maintenance from
2026-10-20, end of life 2028-04-30; 24.22.0 of 2026-10-14 bundles npm 11.19.1); 26 is Current and becomes Active LTS on
2026-10-28 (end of life 2029-04-30; 26.11.0 of 2026-10-07 bundles npm 11.20.0); 25 is end of life. Google's `google-24`
builder offers 22, 24 and 26; Cloud Run's own `nodejs26` runtime is still Preview, which does not matter to a platform
that builds its own images [F]. So the platform accepts **22, 24 and 26**, defaults to the newest Active LTS on the day
a contract is drafted, and has two cliffs to put in the runbook: 2027-04-30 for 22 and 2028-04-30 for 24.

What a supported Node brings without any package: the test runner (`node --test`, stable since 20.0.0, with a JUnit
reporter since 20.8.0 and a documented default file pattern), `--env-file-if-exists` (22.9.0; no longer experimental in
22.21.0 and 24.10.0), type stripping for TypeScript (stable in 24.12.0 and 25.2.0; still a release candidate on 22),
SQLite (`node:sqlite`, unflagged in 22.13.0, a release candidate in 24.15.0 and 25.7.0, renamed `DatabaseSync` to
`Database` in 26.11.0 with the old name kept as a documentation-only deprecated alias), and the permission model
(`--permission`, stable on 22, 24 and 26) [F]. Corepack, which installs pnpm and Yarn from a `packageManager` field, is
no longer distributed with Node from 25.0.0 [F]; this matters for anything beyond npm (4.2).

The application needs 22.13 or later for `node:sqlite` and 22.9 or later for `--env-file-if-exists`; 24 is the right
default for it today, 26 from the end of the month.

The Cloud Run facts that shape a Node service (all from Google's pages of 2026-10-13 [F]): `PORT` is injected (8080 by
default) and the container must listen on `0.0.0.0`, "should not listen on `127.0.0.1`", and be listening within four
minutes; on shutdown Cloud Run sends `SIGTERM` to every container and waits ten seconds before `SIGKILL`, and in the
second-generation environment the container command is the init process, so there is no `--init` to forward signals;
the filesystem is writable, in memory, counts against the instance's memory and is gone when the instance stops; "the
size of your container image does not affect container startup times or request processing time"; startup CPU boost is
on by default for new services and Google measured "up to 30%" faster starts for Node; the default concurrency is 80 and
"Node.js is inherently single-threaded"; a request may run up to 60 minutes; the response-size limit of 32 MiB does not
apply to chunked or streamed responses, and server-sent events have been supported since 2020. Google's Node page adds
one rule the platform will enforce: "Start your application directly using `node index.js` instead of `npm start`, as
`npm` adds extra latency" (npm also does not forward signals, per Node's own Docker guidance) [F].

Memory is the one Node-specific number worth knowing. Since 12.7.0 Node reads the cgroup limit and sizes the V8 heap from
it: on 64-bit, half of the limit, clamped between 256 MiB and 4 GiB (V8's `heap.cc` on main; Red Hat measured 520 MiB of
heap for a 1 GiB container on Node 20) [F]. A 512 MiB instance, the platform's default and Cloud Run's minimum in the
second-generation environment, therefore gives Node a 256 MiB heap by default, and Google's own Node buildpack sets
`--max-old-space-size` to 80 percent of the limit in every image it builds [F]. Node 22.21 and 24 also accept
`--max-old-space-size-percentage`. Buffers live outside the heap, so an instance can still be killed below the heap
limit; Cloud Run ends in-flight requests with a 500 and logs "Memory limit of N MiB exceeded" when that happens [F].
The platform's Node image sets nothing by default and the contract's `resources.memory_mib` stays the knob; the note
goes into the contract page.

### 4.2 What the platforms that deploy Node from source actually do, and the reader that follows

The detection code of Google's buildpacks, Heroku's classic and Cloud Native buildpacks, Railway's Railpack and
Nixpacks, Fly.io's scanner and Dockerfile generator, Paketo's Node buildpacks, Microsoft's Oryx and the documents of
Vercel and Render were read [F]. They agree on four things: `package.json` is the trigger; the lockfile names the
package manager; `scripts.start` is the start command; `PORT` comes from the environment. They disagree on everything
else, and the disagreements are exactly where a deterministic reader (D34) should refuse rather than guess:

- **The Node version.** Google reads `GOOGLE_NODEJS_VERSION`, then `engines.node`, then a per-stack default (22 on Ubuntu
  22.04, 24 on 24.04) and ignores `.nvmrc` and `.node-version` entirely; Paketo and Railpack read both files but in
  different orders; Render puts `.node-version` above `engines.node`, Nixpacks the reverse; Heroku, Vercel and Render
  default to 24 and resolve a range to the highest major that satisfies it, and Heroku warns on a range with no upper
  bound.
- **The lockfile.** Google generates one when it is missing (`npm install --package-lock-only`) and warns; Railpack runs
  plain `npm install` even with a lockfile; Heroku's Cloud Native buildpack refuses without one; Heroku's classic
  buildpack refuses when there are two, or when `packageManager` and `engines.*` name different managers.
- **The start command.** Heroku's release script emits `web: npm start` unconditionally; Google's npm buildpack falls
  through `scripts.start`, `server.js`, `main`, `index.js`, while its yarn, pnpm and bun buildpacks run `<pm> run start`
  with no fallback at all; Paketo refuses ("no start script in package.json") unless one of twelve conventional files
  exists. Nobody inspects what `scripts.start` contains, except Fly's generator, which patches `fastify start` to add
  `--address 0.0.0.0`.
- **The port and the host.** Only flyctl scans the source for `process.env.PORT || N`. Fastify's documented default host
  is `localhost`, which Cloud Run cannot reach; nobody checks for it.
- **Install scripts.** Google's buildpack runs `npm ci --quiet --no-fund --no-audit` with scripts on; so do Heroku and
  Railpack; only Railpack's optional prune step passes `--ignore-scripts`.

The reader for the platform takes Heroku's refusals, the Cloud Native rule "no lockfile, no install", Paketo's explicit
source order for versions, Google's start-command chain cut short at `main`, and adds two checks no platform makes: of
what the start script contains, and of what the listen call does. Every answer below is the first match in its row;
"refuse" names the file and the fix, as D34 requires.

| Question | Where the answer comes from, first match wins | When nothing says |
|---|---|---|
| Which Node? | the Dockerfile's `FROM node:X`; `.nvmrc`; `.node-version`; the `nodejs` line of `.tool-versions`; `engines.node` (a range resolves to the highest supported major that satisfies it; no upper bound is noted); `devEngines.runtime` | the newest Active LTS, named in the contract |
| Which packages? | `package-lock.json` (version 2 or 3) or `npm-shrinkwrap.json`, installed with `npm ci`; a `yarn.lock`, `pnpm-lock.yaml` or `bun.lock` is refused in this phase with the fix (a `package-lock.json` beside it, or the later item) | the platform locks it, as it does for Python (D27): `npm install --package-lock-only --ignore-scripts` with a three-day minimum release age, in a container of the service's Node with npm 11.10 or later (Node 22 bundles npm 10.9, which has no minimum release age), into `apps/<service>/package-lock.json` |
| What starts it? | the Dockerfile's `CMD`; the Procfile's `web:`; Compose's `command`; `scripts.start` when it is `node [flags] <file> [args]` (an `--env-file*` flag is harmless); `main`; `server.js` or `index.js` at the root | refused: say the start command |
| Which port? | Compose `ports` (the container side); one `EXPOSE`; `--port` or `-p` in the start command; a literal in the entry file's `listen(` | 8080, passed in as `PORT` |
| Health check? | a Compose `healthcheck`; a route literal matching `/health`, `/healthz`, `/ready`, `/live`, `/ping` or `/status` (Express, Fastify, Koa, Hono and Hapi route calls, NestJS controllers, Next.js API files, `req.url ===` in a plain server) | none: Cloud Run's TCP check, and the release says the HTTP check is off |
| Settings and needs? | `process.env.NAME` reads in the code, Compose, `.env.example`; a Postgres service in Compose | names are listed for a person to fill in; values are never read |
| Install scripts? | the lockfile's `hasInstallScript` entries, kept only where the repository's own `allowScripts` pins them (`name@version: true`) | none run (4.3) |
| Tests? | `scripts.test` unless it is npm's placeholder (`echo "Error: no test specified" && exit 1`); `node --test`'s default patterns; a Jest, Vitest, Mocha, AVA or tap configuration | none: said plainly, never invented |

It refuses, beyond D34's list: a start script that uses `nodemon`, `ts-node`, `tsx`, `node --watch`, a development
server (`vite`, `next dev`, `nest start --watch`), `concurrently`, a shell chain or `sh -c`; a `.ts` entry on a Node
below 24.12 or a project that needs a build (`scripts.build`, `tsconfig.json` with `typescript`, or Next, Nest, Remix,
SvelteKit, Astro or Nuxt in the dependencies), with the fix "commit the built output, run it under Node's type
stripping, or build it with a Dockerfile of your own" (a build step with development dependencies in a build stage is
the later item); a listen call on a literal port with no `process.env.PORT`, on `127.0.0.1` or `localhost`, or a Fastify
`listen` without `host: '0.0.0.0'`; a static site (Vite, Create React App, Angular, Astro without a server) with "the
platform serves web services"; two lockfiles, or `packageManager` and `engines.*` naming different managers; a lockfile
entry without `integrity` or whose `resolved` is a git URL, a tarball outside the registry, or a `file:` or `link:`
path; `bundleDependencies`; a workspace (`workspaces`, `pnpm-workspace.yaml`, `turbo.json`, `nx.json`) without a service
path, with the list of packages; a committed `.npmrc` or `.yarnrc.yml` with a literal `_authToken`; `engines.iojs`.
It ignores with a note a committed `node_modules/`, `dist/` or `.next/`, and a Procfile when a Dockerfile exists.

The research gives this design its ceiling, as it did for Python: environment construction is the single largest failure
class for automated setup (Multi-Docker-Eval: Docker build errors are 36 percent of failures), and the problem the
authors name for JavaScript is "fragmented test frameworks that complicate test entry point identification" [F]. A
reader that says "tests: none" plainly, and that refuses the start script it cannot read, is the right answer.

### 4.3 Installing dependencies safely: the year npm changed its defaults

The incidents of 2025 and 2026 share one shape (primary write-ups [F]): a phished maintainer or a long-lived token, a
malicious version that lives one to four hours (chalk and debug on 2025-09-08: eighteen packages with "more than 2
billion downloads per week", live "roughly two hours"; Nx on 2025-08-26: four hours, detected because the versions lacked
provenance; Axios in March 2026: about three hours; `@antv` in May 2026: 639 versions in about an hour) or, for the
worms, days (Shai-Hulud, 2025-09-14 to 16, "500+ compromised packages" removed, a `postinstall` that ran TruffleHog on
the host and republished up to twenty packages per maintainer; Shai-Hulud 2.0, 2025-11-21 to 27, "~700" packages, moved
to `preinstall` so that the payload runs even when the install later fails; ChainDrop, 2026-08-04, which also committed
`.vscode/tasks.json` and `.claude` hook files into repositories it reached), and a lifecycle script that runs the payload
the moment anyone installs. Three lessons are load-bearing for the platform: every worm ran from an install script;
provenance says which pipeline built a package and not that it is safe (`@redhat-cloud-services` carried valid SLSA
provenance; so could any package published from a compromised pipeline); and a cooldown of one day would have blocked
every single-version incident, three to seven days most of each worm's window.

npm's answer, as shipped (npm's changelog and command pages, read 2026-10-19 [F]): classic tokens had all been revoked by
2025-12-09 and write tokens now live at most 90 days; trusted publishing with OIDC from GitHub-hosted runners has been
generally available since 2025-07-31; `min-release-age` (in days) arrived in 11.10.0 on 2026-02-11; the `allowScripts`
field in `package.json` arrived in 11.16.0 (2026-05-27) as a warning, and **npm 12.0.0 (2026-07-08) blocks dependency
lifecycle scripts, git dependencies and remote tarballs by default** unless the root package's `allowScripts` policy
allows them, with `npm install-scripts approve` writing pinned `name@version: true` entries and `strict-allow-scripts`
turning an unreviewed script into an error. The application's `"allowScripts": {"onnxruntime-node@1.30.0": true,
"protobufjs@7.6.6": true}` is exactly that field, which suggests its author already runs npm 11.16 or later. Two facts
temper the picture: no Node line bundles npm 12 yet (24.22 and 26.11 carry 11.19 and 11.20, where the policy only warns;
22.23 carries 10.9, which has no policy at all), and `npm ci` verifies the lockfile's `integrity` hashes but its behaviour
on an entry without one is undocumented (pnpm silently skipped verification in that case until CVE-2026-50021 of June
2026) [F]. The platform therefore does not rely on the bundled npm's policy: it installs with `--ignore-scripts` on every
npm, runs the scripts of the contract's list afterwards by name (`npm rebuild <name@version>`, which the npm documents
describe as the way to "explicitly choose which packages to build" after an install with `--ignore-scripts`), and
refuses a lockfile entry without `integrity`.

Install scripts and this application: `onnxruntime-node@1.30.0` ships the CPU binaries for Linux, macOS and Windows
inside its tarball (301 MB unpacked), and its `postinstall` exists to download the CUDA and TensorRT provider libraries
from NuGet on Linux x64 only, which a CPU-only Cloud Run service never loads; with scripts off the package works as it is
[F]. `protobufjs@7.6.6`'s script (`scripts/postinstall.js`, 32 lines) only reads the parent project's `package.json` and
prints a warning when the parent pins protobufjs with a range other than `~`; it writes nothing [F]. The reader will
therefore draft an empty list for this application and say why.

The audit, the pip-audit slot: `npm audit` sends the lockfile's names and versions to the registry and cannot run offline;
its noise is documented (Abramov, 2021: "99%+ false positive rate" in his projects, mostly development dependencies) and
whether its registry proxy returns the malware advisories GitHub now publishes is not stated anywhere [F]. OSV-Scanner
(2.7.0 of 2026-10-12, a checksummed binary, provenance attested) reads `package-lock.json` directly, carries OSV's
`MAL-` records from the OpenSSF Malicious Packages repository, exits 1 on findings and 128 on an empty lockfile, and
also reads `pnpm-lock.yaml`, `yarn.lock` and `bun.lock` for the day those arrive [F]. Trivy's image scan finds every
package under `node_modules` by its `package.json` and emits `pkg:npm/` entries in the SBOM; its data for npm is the
GitHub Advisory Database and the Node.js Security WG, not OSV, so it is not where malicious packages appear first [F].
Artifact Analysis scans Node.js packages in images automatically and on demand, from the GitHub Advisory Database for
vulnerabilities and the OpenSSF repository for malicious packages, the latter "for language packages within container
images" since 2026-08-07 [F]. Coverage, then: a known vulnerability is caught by all of them; a malicious version listed
in OSV by OSV-Scanner and Artifact Analysis; a typosquat only once someone has filed a record; a lifecycle-script payload
by no scanner at all, which is why the scripts never run.

Cooldowns: pnpm added `minimumReleaseAge` in 10.16 and turned it on at one day in pnpm 11; Dependabot has waited three
days before a version-update pull request since 2025-07-01, by default; Renovate documents three days for npm because a
version under 72 hours old can still be unpublished [F]. The platform compiles a lock only when a repository has none;
there it passes `min-release-age=3`, with npm 11.10 or later in the locking container whatever the service's Node (Node
22 bundles npm 10.9, where the option would have no effect), and the contract page tells a developer with Dependabot that the default cooldown
already does this for them (and that a longer npm cooldown than Dependabot's makes the merged pull request fail
`npm ci`).

### 4.4 The image and the running container

Node's own Docker guidance (nodejs/docker-node, the Node security page) and Docker's agree with the platform's Python
Dockerfile line by line [F]: a slim Debian base pinned by digest (`node:24-slim` is `24-bookworm-slim`, Debian 12, about
81 MB compressed for amd64 on 2026-10-14; the Alpine images use musl and "software will often run into issues", which
matters for this application: ONNX Runtime publishes glibc builds, its Python wheels tagged `manylinux_2_28`, and
documents no musl build for `onnxruntime-node`, so its bundled binary should be expected to fail on Alpine); dependencies before the code; `npm ci
--omit=dev`; `NODE_ENV=production`; a non-root user (the image has `node` as uid 1000; the platform's numeric 65532, the
`nonroot` of Google's distroless images, works as well); an exec-form `CMD ["node", "server.js"]`, never `npm start`,
because "Node.js was not designed to run as PID 1" and npm "swallows" signals; a `.dockerignore` that keeps
`node_modules`, `.git`, `.env` and `.npmrc` out. The platform's deny-list already covers the last three; `node_modules`
joins it. hadolint's npm rule (DL3016) fires only on `npm install <package>`, so `RUN npm ci --omit=dev --ignore-scripts`
is clean; OpenSSF Scorecard counts `npm ci` as pinned [F]. Google's distroless `nodejs24-debian13` and Chainguard's
`node` are shell-less alternatives; both are tagged `latest` only (Chainguard's version tags are paid), so pinning is by
digest either way, and neither adds anything the policy gate does not already check. The platform keeps `node:X-slim`.

Shutdown: with the container command as PID 1 and ten seconds before `SIGKILL`, the one thing a Node service must do is
handle `SIGTERM` itself (`server.close()`, then exit); Google's own write-up says a process without a handler "is
terminated instantly", which for a request in flight means an error [F]. The contract page will say so, and the reader
notes a server with no `SIGTERM` listener. Node's default `keepAliveTimeout` is five seconds; the usual reverse-proxy
advice is to set it above the proxy's idle timeout, but Google documents no such figure for Cloud Run's front end, so
the plan records it as unverified rather than prescribing a number.

The permission model (`node --permission --allow-fs-read=... --allow-fs-write=/tmp`) is stable on 22, 24 and 26 and
restricts the filesystem, child processes, workers, native addons and WASI; on 22 and 24 it does **not** restrict the
network (`--allow-net` exists only from 25.0.0 and is still "Active development" in 26.12), and Node's documents call it
"a 'seat belt' approach" that "does not provide security guarantees in the presence of malicious code" [F]. For this
application it would need `--allow-addons` (the ONNX binding) and `--allow-child-process` (the admin page's test runner),
which reopens most of what it closes. It cannot replace the egress deny or the Dockerfile policy; the plan leaves it as a
later opt-in with `--permission-audit`, which logs what an unreviewed application touches without denying anything.

Google's buildpacks remain an option for reviewed code only: the `google-24` builder offers 22, 24 and 26 and takes
`GOOGLE_NODEJS_VERSION` and `GOOGLE_ENTRYPOINT` exactly as the Python path takes their Python equivalents, but its npm
buildpack runs install scripts (no `--ignore-scripts`), generates a lockfile when one is missing, and downloads the Node
runtime from `dl.google.com` at build time, so `build.network: none` cannot work and the platform's script rule cannot be
applied [F]. For `trust: unknown` the platform Dockerfile is the only path.

## 5. Question 2: what this application needs beyond Node

### 5.1 Four collisions

Read against Cloud Run's contract, the application does four things a stateless, scale-to-zero, egress-denied container
cannot do as it is: it reads a corpus and a model from local disk that are not in the repository; it keeps a database and
a cache on local disk; it calls Anthropic, OpenAI and the Hugging Face Hub over the internet; it identifies people by a
header and expects Microsoft accounts. Two smaller things follow from the first two: an in-memory rate limiter and a chat
log on disk, both per instance.

### 5.2 Files and models

The platform's build runs with no cloud credentials, and the platform repository is public, so the hospital's content
(the list export committed today, the full index of pages and documents, and the embeddings made from them) can neither
be fetched at build time nor live in the repository. The sound place is a bucket the platform already provisions
(`needs.buckets`), mounted read-only into the container: Cloud Run's Cloud Storage volume mounts have been generally
available since 2024-08-27, use Cloud Storage FUSE, take a read-only flag, "can slightly increase your Cloud Run container
cold start time", fail the start if the mount takes over 30 seconds, and need `roles/storage.objectViewer` on the runtime
identity; FUSE itself is free and the reads are ordinary storage operations [F]. The application reads its corpus from a
fixed path under `data/index/`, so a mount there needs no code change; the model (34 MB for the quantized ONNX file plus
about 1 MB of tokenizer files, from the Hub's `Xenova/bge-small-en-v1.5`) goes in the same bucket, and the application
sets `env.allowRemoteModels = false` and `env.localModelPath` to it (transformers.js reads no environment variables at all,
so this is a code change of two lines) [F]. The embeddings cache is computed once by a script and stored beside them (its
path, `data/embeddings.json`, is fixed in the code, so one more line points it at the mount), so startup does no
inference. Baking the model into the image would also work (Google: image size does not affect cold
start) but needs a Dockerfile of the application's own, since the platform's has no build hook; the bucket serves both.

What is written at run time (`data/sophia.db`, `data/logs/`, `data/eval/`) goes on an in-memory volume with a size limit,
so that a runaway write fails with `ENOMEM` instead of killing the instance [F]. Google's FUSE page says a bucket mount
"shouldn't be used as the backend for storing a database" and "does not support file locking", which settles 5.3.

### 5.3 A small database

Each Cloud Run instance has its own in-memory copy of `data/sophia.db`, lost at scale to zero, at every release and at
any replacement. Three sound answers, cheapest first [F]: (1) **Litestream** as a sidecar container in the same service,
replicating the file to the application's backup bucket and restoring it at startup, with one instance at most (its
author: "We assume a single writer"; replication is asynchronous, so a crash loses the last sync interval); it is
maintained (releases about monthly, from 0.5.9 in February to 0.5.17 on 31 August; the release page shows no year),
picks up the instance's credentials on Cloud Run, and costs only storage
operations; no application change. (2) **Firestore**, which the platform already provides, free up to 1 GiB and 50,000
reads a day, reachable through Private Google Access; it means replacing the 434-line SQLite layer. (3) **Cloud SQL
Postgres**, about $8.57 a month at the platform's floor and a rewrite as well; not the answer here. `max_instances: 1`
is a lab-grade setting: Google says the maximum "can be exceeded for a brief period" during spikes and rollouts, so the
sidecar could rarely see a second writer; for a handful of users that is acceptable and the runbook says so.

A platform feature falls out of (1): `state: sqlite` with a path, which the service module turns into the sidecar, the
restore step, the volume and the instance limit, with the recovery drill of Phase 6 extended to it. It is the first
multi-container service the platform runs, which is why Phase 19 has a trial.

### 5.4 Streaming

Server-sent events need nothing from the platform: Cloud Run streams responses, the 32 MiB limit does not apply to
chunked responses, a stream is a request bounded by the request timeout (the contract's `timeout_seconds`, 60 by default,
300 at most today; an Opus answer with retrieval fits, a long one may not, so the contract page says to raise it), and
Cloud Run proxies to the container as HTTP/1 unless h2c is asked for [F]. Whether IAP passes a stream through unbuffered
is stated nowhere in Google's IAP pages; Phase 19's trial tests it in ten minutes.

### 5.5 The model API without the internet

Claude is on Vertex AI: Google's model page (2026-10-15) lists `claude-opus-5-5`, `claude-opus-5`, `claude-sonnet-5-5`,
`claude-fable-5-1` and more, with the same identifier strings the application uses, and three kinds of endpoint: global
(`aiplatform.googleapis.com`, `region: "global"`, no premium), multi-region (`aiplatform.us.rep.googleapis.com`, plus 10
percent) and regional (which carry only Sonnet 4.6 and earlier) [F]. Private Google Access, which is what the lab's
network has instead of NAT, "doesn't support regional and multi-regional endpoints (endpoints that end in
`rep.googleapis.com`)" [F], so the global endpoint is the one an egress-denied service can reach, and it is the one
without a premium. The SDK side is a one-line swap (`@anthropic-ai/vertex-sdk`'s `AnthropicVertex` reads
`ANTHROPIC_VERTEX_PROJECT_ID` and `CLOUD_ML_REGION` and signs with the runtime identity through the metadata server; no
key) [F]; the runtime identity needs the Vertex user role, and a person must click **Enable** once per model on its Model
Garden card [F]. What the Vertex route lacks is documented: the server-side `fallbacks` parameter (the application's
configuration already says "Set to 0 on Bedrock/Vertex/Foundry"), the Files, Batches and Admin APIs, and the server-side
tools; adaptive thinking, `output_config.effort`, streaming and prompt caching are supported [F].

Prices, from the Billing Catalog on 2026-10-19, per million tokens on the global endpoint: Claude Opus 5.5 $4 for input,
$20 for output, $0.20 for a cache read and $5 for a five-minute cache write; Claude Sonnet 5.5 $2, $10, $0.10 and $2.50;
the `us` endpoint adds 10 percent to each. These are the same as Anthropic's list for the direct API. The catalog has no
SKU for Claude Opus 5, the application's default model, although Google's page lists it; before relying on it, its price
must be read again or the application moved to Opus 5.5, which its code and price table already handle.

What a question costs: two model calls, both on the answer model unless `REWRITE_MODEL` says otherwise. The search
rewrite sends a system prompt of about 670 tokens with the conversation; the answer sends a system prompt of about 1,700
tokens (which the application marks for caching), up to eight passages of at most about 280 words each with their
headers and links, the site's facts, the person's profile and up to ten earlier turns, and thinks adaptively at low
effort. From those sizes, a typical question sends about 7,500 input tokens across the two calls and gets about 850
back: about five cents on Opus 5.5, from three cents for a first short question to ten for a broad one late in a
conversation, and half that on Sonnet 5.5; a hundred questions a day is about $5 a day, which is the real bill of this
application. This is an estimate from the prompts, not a measurement: the application's own admin page records the cost
of every answer (its "Claude spend" card, added in 2.3.0), which is the figure to trust after the first week. Two
consequences for the lab: Vertex spend lands in the project's billing export, so the weekly cost report sees it and the
budget's cap closes ingress when it runs away, which the direct Anthropic API never gave; and it lands at project level:
the platform attributes cost by the service's labels, and whether a model call can carry one was not checked, so the
per-application share is a note until the platform attributes it.

The two things that still need the internet are the OpenAI backup and the Hub download, and the cheapest answer is to
need neither: the model comes from the bucket (5.2), and the backup provider is either dropped for the lab's use or moved
to a Google-hosted model on the same endpoint. If the backup must stay, the options and their prices [F, catalog]: Cloud
NAT ($0.0014 an hour for the gateway, $0.005 an hour for its address, $0.045 per GiB; Google warns of "cold start delays
of 30s or more" with Direct VPC egress) plus Cloud NGFW Standard FQDN egress rules to allow `api.openai.com` only
(Standard is billed on traffic; whether its FQDN rules apply to Direct VPC egress is not documented and would need a
test); Secure Web Proxy with a URL list is the designed tool and costs $1.25 an hour, about $912 a month, which rules it
out. The platform's answer stays `egress: internet` or nothing, and the plan records the filtered option as not now.

### 5.6 People who sign in with Microsoft accounts

The platform's sign-in for people is IAP with listed Google accounts (`exposure: lab-members`); programs present a
Google identity token. Google's pages (2026-10-13) settle what the application's users can and cannot do [F]: IAP can
take external identities through Identity Platform (Microsoft among its providers; free to 50 monthly active users on
the OIDC tier, then $0.015 each, from the catalog), but those identities get no programmatic access, access control
moves from IAM into the application, a sign-in page must exist, and the documented path is IAP in front of a load
balancer rather than the Cloud Run-native IAP the platform uses. A browser extension or a SharePoint page is a
cross-origin caller, and "there is no way to share cookies between `source_domain` and `target_domain`" for IAP, so
neither can call an IAP-protected service at all; and Google documents no way for a browser to obtain a Google identity
token with the service's URL as audience. Google's own answer for Microsoft users is an application that verifies Entra ID tokens itself behind a
service that `allUsers` may invoke, which is the public exposure the platform refuses by design.

So the first deployment is for lab members, signing in through IAP, using the replica the server serves at its own
origin; the extension stays a local tool; and the application reads who the person is from IAP's signed assertion
instead of the `X-Sophia-User` header, which today lets any caller be the admin. Opening it to the hospital's staff is a
decision about exposure and about the hospital's content, not about Node, and the plan leaves it with Brian and the
institution (section 7).

### 5.7 What it costs

Idle, nothing to speak of: the service scales to zero, the bucket holds a few hundred megabytes at most ($0.020 per
GiB-month beyond the free 5 GiB, so cents at worst), the sidecar's replication is a few storage operations an hour. In use, the model calls dominate (5.5). The platform features
of Phase 19 add no idle cost; Cloud SQL and NAT, which would, are not in the plan.

### 5.8 Verdict on question 2, and the application's own list

Two platform features are worth building for every data-bearing application: a read-only bucket mount and a replicated
SQLite file; one more, the Vertex route, makes the egress deny compatible with an application that calls Claude. The rest
is the application's, and none of it is a rewrite:

1. `HOST=0.0.0.0` in the contract's `env` (no code change).
2. The corpus, the model and the embeddings cache in the bucket; two lines pointing transformers.js at the mount and
   turning remote models off, and one moving the embeddings cache's path there; a script that writes the embeddings
   cache once; the committed list export removed from
   the repository before it becomes public.
3. The database on `state: sqlite` (no change) or on Firestore (a rewrite of `server/store.mjs`).
4. The chat log to standard output as JSON, which Cloud Logging collects, instead of a file.
5. The Vertex client (one line), `REFUSAL_FALLBACK=0`, the backup provider off or Google-hosted, the model on Opus 5.5 or
   its Vertex price confirmed.
6. The user's identity from IAP's assertion, not from a header; the admin role from the same place.
7. A public GitHub repository, since the platform refuses private ones while it is public itself; the hospital's data
   stays in the bucket.
8. A `SIGTERM` handler, and `engines.node` set to 24.

## 8. Limits of this review

The application was read, not run: its tests, its startup time with the model, and its memory under load are untested
(a few hundred MiB is a guess, to be measured on the first revision), and the cost of a question in 5.5 is estimated
from its prompt and passage sizes, not measured. Google documents neither the keep-alive its front

benchmark figures of 4.2 come from repositories that are not the lab's.
