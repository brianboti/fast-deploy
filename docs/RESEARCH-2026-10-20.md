# Any Python or Node.js web service, as it is: Fast Deploy 1.21.0 against research and practice

Written 2026-10-20 as a read-only review. Nothing in the code was changed; the plan it produces is in `docs/ROADMAP.md`
(Phases 20 to 22, decisions D48 to D56). The question asked was the operator's: the platform must not look like a thing
customised for one Node.js application; it must be able to deploy any Node.js or Python web service automatically,
without a change to that application's code or repository. Two questions follow from it: how general the platform is
today, measured rather than claimed; and what the platforms that deploy arbitrary repositories from source do that this
one does not, and whether their choices are better for the lab.

Method: the platform's reader and its rules were read in full (`labdeploy/reader.py`, `labdeploy/node.py`,
`labdeploy/scaffold.py`, `labdeploy/dockerpolicy.py`, the developer contract, the two earlier reviews), every refusal and
every default listed. Then the reader itself was run, read-only and offline, over 33 public repositories chosen as
typical Python and Node.js web services (section 4): the first measurement of the platform's generality, which the review
of 2026-10-19 noted did not exist. Five themed searches then ran in parallel (source-based builders: Google's buildpacks,
Cloud Native Buildpacks, Heroku, Paketo, Railpack and the Dockerfile generators; the hosted platforms: Railway, Render,
Fly.io, Azure, AWS App Runner, Coolify, Dokku, CapRover, Vercel and Netlify; the Node.js ecosystem's conventions; the
Python ecosystem's conventions; Cloud Run's own container contract and what a deploy flag, a sidecar or an image wrapper
can take over), each returning only what it had fetched, about 250 sources in all. Section 9 marks each source as
fetched from the official page or source file (F), seen in a secondary source (S) or unverified (U). Two limits: the 33
repositories were read, never built or run, so "accepted" means the reader drafted a valid contract, not that the first
revision served; and the sample is small and chosen by hand (section 8).

Acronyms: CNB (Cloud Native Buildpacks), EOL (end of life), IAP (Identity-Aware Proxy), LTS (long-term support), PaaS
(platform as a service, the hosted platforms of section 6), SPA (a single-page application, a front-end site with no
server of its own).

## 1. The short answer

**The platform is not customised for one application, but it is far narrower than "any Python or Node.js web
service".** Nothing in the code is Sophia's: the only mentions are two package names in a table of packages whose
install scripts are not needed, and comments. Every rule the reader applies is general. The narrowness is the design
choice made on 2026-10-16 (D34) and repeated for Node.js on 2026-10-19 (D46): **refuse rather than guess**. The survey
of section 4 measures what that choice costs. Of 33 public repositories, the reader takes **3** as they are. It refuses
the other 30 for 60 reasons, and when each reason is classified, the picture is this:

| Why the reader refused | Refusals | Repositories | What it is |
|---|---|---|---|
| A Dockerfile that runs as root | 9 | 9 | the lab's rule for code nobody reviewed (14.1); Google's own Cloud Run samples run as root |
| The service needs a build first (Next.js, NestJS, TypeScript, `npm run build`) | 8 | 5 | a later roadmap item; every other platform builds |
| No application object the Python reader knows | 8 | 8 | Streamlit, Gradio, aiohttp, scripts started with `python main.py`, and two the reader did not find |
| A file read as a committed secret | 8 | 5 | 4 are false positives (`.env.local.example`), 4 are real environment files |
| A Node.js line at end of life (16, 18, 20) | 5 | 5 | 3 in version files the platform could override, 2 in the repository's own Dockerfile |
| A pnpm or Yarn lockfile | 4 | 4 | a later roadmap item |
| A workspace (pnpm, nx, `workspace:` dependencies) | 3 | 3 | a later roadmap item |
| No dependency manifest the reader knows | 3 | 3 | a `requirements/` folder, a root above the services, a demo without one |
| `requirements.txt` that includes another file (`-r requirements/base.txt`) | 2 | 2 | a reader gap |
| A notebook in the repository | 2 | 2 | a misleading message: the real reason was the entry point |
| Other, one each | 8 | 8 | Python 3.9 in a Dockerfile; a settings file mistaken for Django; a chained start script; Fastify on localhost; a literal port; a front-end site; a helper script that listens on 127.0.0.1; `COPY .env` |

Read against what Cloud Run itself requires (section 5) and what the other platforms do (section 6), about two thirds of
those refusals are the platform's own choices, not the container's needs: things a deploy flag, a build stage, a
sidecar, a wider ladder or a fixed regular expression takes over with nothing added to the repository. With the changes
proposed in section 7, the same sample reads as **about 20 of 33 accepted**; the remaining 13 each need one answer from a
person that no platform can read from the files (which folder, which command, a real `.env` to rotate, an end-of-life
base image in the repository's own Dockerfile). That is the honest ceiling of "without changing the code or the
repository": Railway, Render and Google reach the same places and ask the same questions there.

Three findings matter most:

1. **The Python side is as narrow as the Node.js side, and it was never measured.** The reader knows eight framework
   constructors and refuses everything else. A research lab's typical applications, Streamlit and Gradio demos and
   scripts started with `python main.py`, are refused with "no application object of a known framework". Google's
   buildpacks, Railpack and Oryx all start those from the dependency that names the framework (section 6.4).
2. **Several refusals guard against things Cloud Run can absorb.** A service that listens on a literal port never
   reading `PORT` is deployable as it is: `gcloud run deploy --port 3000` sets both the container port and `PORT` [F].
   A service bound to `127.0.0.1` is reachable through a proxy sidecar on the ingress port, a pattern Google documents
   with Nginx [F]. A start command with `&&` runs under a tiny init. None of these needs a code change.
3. **The reader's own bugs cost as much as its policies.** `.env.local.example` is read as a secret; a `settings.py`
   that mentions Django in a comment is "a Django project"; `-r requirements/base.txt` is refused; the entry file of a
   large application is never read because sixty shallower files come first; a notebook anywhere hides the real
   refusal. Each is a line to fix.

What does not change: the merge of the contract by a person as the review (D32), the gates that stop a malicious
package or a working key, containment for code nobody reviewed, secret values entered by the operator, and the lab's
rule that nothing is public. The platforms that "deploy anything" put all of that on the developer; this one keeps it,
and still reaches most of their coverage.

## 2. Where the platform stands

Version 1.21.0 on main (`75a6d5e`), 848 tests; the controller machine runs 1.20.11. The platform deploys a Python or
Node.js HTTP service to Cloud Run from a repository that follows the contract, or as it is (1.15.0 and 1.20.0): the
reader draws a contract from the files, a person merges it in the platform repository, and the platform's own pipeline
releases it. That mode already satisfies the operator's framing on paper: nothing is written into the application
repository, the contract lives in `apps/<service>/platform.yaml`, locks the platform makes live beside it.

What the reader reads today, first match wins (the full ladders are in `docs/DEVELOPER-CONTRACT.md`):

- **Python**: the Dockerfile's `FROM python:X.Y`, `.python-version`, `runtime.txt`, `Pipfile.lock`, `requires-python`,
  else 3.12; dependencies from `requirements.lock`, a hashed `requirements.txt`, `uv.lock`, `poetry.lock`,
  `Pipfile.lock`, the pip part of `environment.yml`, `requirements.txt`, `pyproject.toml`; the entry from the
  Dockerfile's `CMD`, a Procfile, Compose's `command`, `[tool.fastapi] entrypoint`, Django's `WSGI_APPLICATION`, one
  module-level object of FastAPI, Starlette, Quart, Litestar, Falcon, Flask or Bottle, or one factory named
  `create_app`, `make_app`, `get_app`, `build_app` or `app_factory`; the port from Compose, `EXPOSE` or the command;
  the health route from Compose or a `/health` literal, else the TCP probe; tests from pytest's files, else "none".
- **Node.js**: the line from the Dockerfile, `.nvmrc`, `.node-version`, `.tool-versions`, `engines.node`,
  `devEngines`, else the newest Active LTS; packages from `package-lock.json` or `npm-shrinkwrap.json`, else a lock the
  platform makes; the start from the Dockerfile, a Procfile, Compose, `scripts.start` when it is `node [flags] <file>`,
  `main`, `server.js`, `index.js`; the port from Compose, `EXPOSE`, the command, or the listen call's literal; the host
  from the listen call; the health route from Compose or a `/health` route; install scripts never, except those the
  contract lists; tests from `scripts.test` or `node --test`.

What it refuses is listed in the contract's two "refuses" paragraphs, and every rule is in the appendix (section 10) with
its class. The grep for anything application-specific finds `onnxruntime-node` and `protobufjs` in the table of install
scripts a Cloud Run service never needs, `onnxruntime-node@1.30.0` as the example in an error message, and two comments
naming Sophia. The rule that a `build` script is refused only when the start file is missing came from Sophia's
repository, and is right for every repository.

The earlier reviews chose "refuse rather than guess" for a reason worth restating: a wrong guess costs a failed first
revision, which the operator then has to read. That was the right call when the platform had no gates. It has them now:
the dependency audit, the image scan, the secret scan, containment and the bake all run before and after a guess, so a
wrong guess is safe, only slow (one build, about $0.26 of scan, a few minutes). The balance can move.

## 3. What the evidence is, and what does not exist

Strong evidence (F): the Cloud Run container contract and the `gcloud run deploy` reference, which say exactly what a
deploy flag can set; the detection code of Google's buildpacks, Railpack and Fly's scanner, read in their repositories;
the documents of Heroku, Paketo, Railway, Render, Azure's Oryx, AWS App Runner, Dokku, Coolify and CapRover; the
reference pages of npm, pnpm, Yarn, Bun, Node's TypeScript support, and of every framework named in section 6; pip, uv,
Poetry, pipenv, PDM, gunicorn's and uvicorn's source for their defaults; Python's version status page.

Measured here: the reader over 33 repositories (section 4), reproducible from the repository names.

What does not exist: a published study of how many real repositories a source-based platform deploys without changes
(each platform publishes its rules, not its hit rate); a Google statement on IPv6 binding (`::`) on Cloud Run; a billing
formula for a sidecar's share of an instance; Render's lockfile selection and install-script behaviour; whether Heroku's
Python buildpack gives any default web process (its release script declares none [F]).

## 5. What "without changing the code or the repository" can mean

Cloud Run's contract [F] is short: listen on the port it gives, on every interface; start within four minutes; handle
`SIGTERM` within ten seconds or lose the requests in flight; treat the disk as memory; build for `linux/amd64`. Everything
else is the platform's to set. The question is which of the contract's demands a platform can meet on the developer's
behalf, read from Cloud Run's own reference pages:

| The container must | Who can make it so | How, without touching the repository |
|---|---|---|
| Listen on the port Cloud Run sends requests to | the platform | `--port N`: "Container port to receive requests at. Also sets the $PORT environment variable" [F]. An app hard-wired to 3000 is deployed with `port: 3000`; it never has to read `PORT` |
| Listen on every interface, not `127.0.0.1` | the platform, usually; else the developer | an environment variable where the app reads one (`HOST`, `HOSTNAME`, `GRADIO_SERVER_NAME`, `NITRO_HOST`, `--server.address`); where it reads none, a proxy sidecar on the ingress port forwarding to `127.0.0.1:N`: "All containers in an instance share a network namespace" and Google's own guide runs Nginx as the ingress container with `proxy_pass http://127.0.0.1:8888` [F]. Only an app that binds loopback and offers no setting and no proxy path needs a line changed |
| Start with the right command | the platform | `--command` and `--args` override the image's `ENTRYPOINT` and `CMD` [F]; the contract's `command` and `args` already do this (13.4) |
| Have its settings and secrets | the platform | `--set-env-vars`, `--update-secrets` as variables or files, `--add-volume` for a bucket [F]; `PORT` is the one name the platform may not set [F] |
| Be probed | the platform | with no probe, Cloud Run adds a TCP startup probe (240 s, one failure) [F]; an HTTP probe needs a path that answers 2xx or 3xx; Google recommends no path, and only the readiness probe defaults to `/` [F]. TCP is the zero-knowledge probe the platform already uses |
| Run as some user | nobody is forced | "Cloud Run runs the container as the root user" when the image names none [F]; non-root is Google's advice, the lab's rule for unreviewed code, and never Cloud Run's requirement |
| Be one process that handles `SIGTERM` | the platform, mostly | in the second-generation environment the command "starts as the container init process" [F]; a shell-form `CMD` is not PID 1 and gets no signal [F]; a tiny init (tini, dumb-init; nothing in Cloud Run's documents forbids them) forwards it to a chain. Draining in-flight requests is the app's (NestJS must opt in [F]; SvelteKit, Nitro and react-router-serve drain [F]) |
| Be built for `linux/amd64`, without a Dockerfile | the platform | `docker buildx build -f -` reads a Dockerfile from standard input and `--build-context app=docker-image://IMAGE@sha256:…` makes `FROM app` an image the platform chose [F]: the mechanism for a wrapper stage (a `USER`, an init) over any image |
| Keep nothing on disk | the developer | the filesystem is in memory and is gone with the instance [F]; a SQLite file or an upload folder needs Firestore, Postgres or a bucket, whatever the platform (4b of the contract) |
| Not call `sudo`, mount or eBPF | the developer | unsupported in both environments [F] |

So the inherent list is short: state on disk, privileged operations, a loopback bind with no setting and no proxy path,
a second long-running process, a build that needs a secret (Strapi and Payload want their keys at build time [F]), and
the choice among several services or several apps in one repository. Everything else in the platform's refusal list is
the platform's.

## 6. What the platforms that deploy from source do

### 6.1 Builders: how a bare repository becomes a container

Google's buildpacks (the path `gcloud run deploy --source` takes, always with `builder:latest`, `google-24` today: Node
22, 24, 26; Python 3.13 and 3.14 [F]) read, for Node.js: `package.json`, else any `.js` file; the version from
`GOOGLE_NODEJS_VERSION`, then `engines.node`, then the builder's default; the manager from the lockfile in the order
Yarn, pnpm, Bun, npm, and with none, `npm install --package-lock-only` with a warning; `npm ci` with every install script
on ("Always run npm install to run preinstall/postinstall scripts" in the source); `npm run build` when a `build` script
exists; the start from `scripts.start`, else `server.js`, `main`, `index.js` [F]. For Python: any `.py` file; the
version from `GOOGLE_PYTHON_VERSION`, then `.python-version` (never `requires-python`); `requirements.txt` over
`pyproject.toml`, then `poetry.lock` or `uv.lock`; the start, on 3.13 and later, from the first of gunicorn, uvicorn,
`fastapi[standard]`, gradio, streamlit or google-adk in the requirements, each with its own command
(`streamlit run main.py --server.address 0.0.0.0 --server.port 8080`; gradio as `python main.py` with
`GRADIO_SERVER_NAME=0.0.0.0`), else `gunicorn -b :8080 main:app`; a Procfile or `GOOGLE_ENTRYPOINT` always wins [F].
Every one of those inputs is a build environment variable, passed from outside the repository [F].

Railpack (Railway's builder, the successor of Nixpacks, which is in maintenance [F]) takes its whole configuration from
the command line or a file anywhere, and emits a build plan that "does not need to be in the same directory as your
app" [F]. Node: the version from `RAILPACK_NODE_VERSION`, `devEngines`, `engines.node`, `.nvmrc`, `.node-version`,
`mise.toml`, else LTS; the manager from `packageManager`, then the lockfile (pnpm, Bun, Yarn Berry, Yarn 1), else npm;
the `build` script runs; the start is `scripts.start`, `main`, `index.js` or `index.ts`; a front-end with no server is
served by Caddy [F]. Python: an entry file (`main.py`, `app.py`, `start.py`, `bot.py`, `hello.py`, `server.py`) or a
manifest; pip, uv, Poetry, PDM and pipenv, each installed frozen without development groups; Django by `manage.py` and
`WSGI_APPLICATION` as `python manage.py migrate && gunicorn <app>:application`; Flask as `gunicorn --bind
0.0.0.0:${PORT:-8000} main:app` only when gunicorn is a dependency; FastAPI as `uvicorn main:app --host 0.0.0.0`; else
`python <main file>` [F].

Heroku's Node.js buildpack requires a lockfile in its CNB form, fails on two lockfiles, resolves `engines.node` (24 by
default), runs install scripts, `heroku-postbuild` or `build`, and makes `scripts.start` the web process when there is no
Procfile [F]. Its Python buildpack installs from `requirements.txt`, `poetry.lock`, `uv.lock` or `Pipfile.lock` with the
matching frozen command, runs Django's `collectstatic` on its own and fails the build when that fails, and declares no
default web process at all: a Procfile is required in practice [F]. Paketo's Node buildpacks try `server.js`, `app.js`,
`main.js`, `index.js` when there is no start script and otherwise refuse; its Python buildpacks set the REPL as the
start unless a Procfile says otherwise [F]. Fly's generator needs a start script and writes a Dockerfile into the
repository; `docker init` is interactive and writes four files [F].

What this says for the reader: the builders agree on the triggers (`package.json`, a `.py` file), on reading the
version from the standard files, on installing frozen from whatever lockfile is there, on running the `build` script,
and on falling through a short list of entry files. They disagree on install scripts (all run them; the platform does
not, and npm 12 now sides with the platform [F]) and on what to do with nothing (Google fails with an exact message;
Oryx serves a placeholder; Paketo starts a REPL). The platform's ladders already follow the builders' order; what they
lack is the builders' breadth (other lockfiles, a build step, the Python frameworks beyond the ASGI and WSGI objects)
and their habit of trying the convention before refusing.

The requirements every one of them puts on the developer, read from their pages [F]: listen on `0.0.0.0` and on `PORT`
or the port you declare; keep the manifest at the root of the folder the platform builds; for Node.js have a `start`
script, for Python a recognisable entry or a typed command; be ready to state the command (every platform has the

application's tests before deploying (CI's job, in Heroku's words [F]); none of them refuses a Dockerfile that runs as
root; none of them audits the lockfile or scans the image before the first revision. Their coverage comes from doing
less, not from reading better.

### 6.3 The Node.js conventions a platform must honour

The facts that decide the Node.js items of section 7, all read in the official pages [F]:

- **Managers.** Corepack is still experimental in Node 24 and "will no longer be distributed starting with Node.js
  v25"; a platform on 26 installs the manager itself. The frozen installs are `npm ci`, `pnpm install
  --frozen-lockfile` (on by default in CI), `yarn install --immutable` (on by default in CI), `bun ci`. Every manager
  can turn install scripts off and keep an allow-list: npm 12's `allowScripts` (dependency scripts "blocked by default"
  since 2026-07-08), pnpm's `allowBuilds` with `strictDepBuilds`, Yarn's `enableScripts`, Bun's `trustedDependencies`
  (which replaces the default list; `[]` means none). pnpm has `minimumReleaseAge` (default a day since v11), Bun
  `minimumReleaseAge`, npm `min-release-age`; Yarn has none found. One service out of a workspace: `pnpm deploy
  --filter`, `yarn workspaces focus --production`, `npm --workspace`, `turbo prune --docker`.
- **Builds.** NestJS needs `nest build` (decorators and parameter properties, which Node's type stripping refuses); Next.js
  needs `next build`, and `output: 'standalone'` gives a `server.js` that runs with no `node_modules`; React Router and
  Remix build to `build/server` and start with `react-router-serve` or `remix-serve`, which read `HOST` and `PORT` and
  close on `SIGTERM`; SvelteKit's adapter-node builds to `build/` and starts with `node build` on `0.0.0.0:3000`; Nuxt's
  Nitro builds `.output/server/index.mjs` with `NITRO_HOST` and `HOST` defaulting to `0.0.0.0`; Astro's Node adapter
  builds `dist/server/entry.mjs`, binds localhost unless `HOST` is set. Strapi and Payload need their secret keys at
  build time.
- **TypeScript.** Node strips types by default since 22.18 and 23.6, stable in 24.12; enums, namespaces with code,
  parameter properties and decorators are refused; TypeScript 5.8's `erasableSyntaxOnly` names exactly that subset. A
  `start` of `tsx src/index.ts` needs tsx at run time, a development dependency.
- **Host and port.** Node's `listen(port)` with no host binds every interface (`::`, which "may cause the net.Server to
  also listen on 0.0.0.0"); Express, Koa, Hono, NestJS and the serve commands above do so. The exceptions: Fastify
  (localhost unless `host` is passed), Astro (unless `HOST`), Next.js standalone (reads `HOSTNAME`, which Docker may set
  to the container's id; the official Dockerfile sets `HOSTNAME="0.0.0.0"`). So `HOST=0.0.0.0` and `HOSTNAME=0.0.0.0` in
  the environment cover every framework but Fastify's own `listen` call.
- **The rest.** V8 sizes its heap from the cgroup limit, and `--max-old-space-size-percentage` exists since 22.21 for
  `NODE_OPTIONS`; `NODE_ENV=production` makes npm omit development dependencies and Express three times faster; Node's
  keep-alive is five seconds and Cloud Run documents no idle timeout; Kubernetes deprecated `healthz` for `livez` and
  `readyz`, and Terminus answers `/health` with 200.

### 6.4 The Python conventions a platform must honour

Read in the official pages and source files [F]:

- **Dependencies.** The frozen installs are `pip install --require-hashes -r`, `uv sync --frozen --no-dev
  --no-install-project`, `poetry install --no-root --only main`, `pipenv install --deploy`, `pdm install --check --prod
  --no-editable`; Hatch locks only when asked (PEP 751 `pylock.toml`); conda's `environment.yml` carries a `pip:` list.
  A `setup.py` or `setup.cfg` is installed with pip, never run. PEP 735 dependency groups are final, and pip 25.1
  installs them with `--group`. `.python-version` is the version file every tool reads; Heroku deprecated `runtime.txt`
  on 2025-02-06; `requires-python` is the fallback. On 2026-10-20, 3.15 and 3.14 are in bugfix, 3.11 to 3.13 in
  security fixes, 3.10 ended on 2026-10-01.
- **Entries.** Flask's own discovery imports `app` or `wsgi` and looks for `app`, `application`, any instance, then
  `create_app` or `make_app`; FastAPI's command line tries `main.py`, `app.py`, `api.py`, `app/main.py`, `app/app.py`,
  `app/api.py` and the names `app`, `api`, then the first instance, and `fastapi run` binds `0.0.0.0:8000` with proxy
  headers on; Litestar autodiscovers `app.py`, `application.py`, `app/__init__.py` and the names `app`, `application`,
  `create_app`; Django's `startproject` writes `WSGI_APPLICATION` and a `wsgi.py` beside `manage.py`. Streamlit starts
  with `streamlit run app.py --server.address 0.0.0.0 --server.port $PORT --server.headless true`; Gradio reads
  `GRADIO_SERVER_NAME` (default `127.0.0.1`) and `GRADIO_SERVER_PORT`; Dash binds `127.0.0.1:8050` and reads `HOST` and
  `PORT`; Panel needs `--address` and `--port`; Chainlit `--host 0.0.0.0 --port`; Shiny `shiny run --host`; NiceGUI
  binds `0.0.0.0:8080` by itself; aiohttp's `run_app` binds `0.0.0.0:8080` by default and `python -m aiohttp.web -H
  0.0.0.0 -P $PORT pkg.module:init` starts a factory; Sanic `--host=0.0.0.0`; Tornado's `listen(port)` takes every
  interface; Bottle and Falcon run under gunicorn.
- **Servers.** gunicorn binds `0.0.0.0:$PORT` on its own when `PORT` is set, else `127.0.0.1:8000`, one worker; uvicorn,
  hypercorn, granian and daphne default to `127.0.0.1:8000`, so the platform always writes the bind. uvicorn trusts
  proxy headers only from loopback unless `FORWARDED_ALLOW_IPS` says otherwise; Django wants `ALLOWED_HOSTS`,
  `CSRF_TRUSTED_ORIGINS` and `SECURE_PROXY_SSL_HEADER` as settings, which only an environment variable the code reads can
  supply.
- **Django's chores.** Heroku runs `collectstatic` at build and fails the build when it fails; Railpack runs `migrate`
  before gunicorn; WhiteNoise is the way static files are served without a web server.
- **Tests and wheels.** pytest's discovery, configuration order and unittest's are documented; no deployment builder runs
  tests. psycopg2 from source needs a compiler and `libpq-dev`; cryptography needs Rust; numpy 1.26.4 has no wheels for
  3.13 and later, so an old pin forces a source build; pip's `--only-binary :all:` and uv's `no-build` refuse source
  builds; a CPU torch wheel is 555 MB.

## 7. What to change, and the decisions

The audit of every rule the reader applies today, classified as in section 4 (the full list is the appendix, section
10): of about 45 rules, 4 are inherent (a port below 1024, nothing that starts the service, a
privileged Dockerfile, state on disk), 17 are policy (committed secrets, dead runtime lines in the repository's own
Dockerfile, non-registry packages, install scripts, the root user, no public exposure, tests as a gate, buildpacks for
reviewed code only), 3 avoid a guess between equals (several Compose services, several frameworks, several factories),
and about 22 are the platform's to take over. The design follows the roadmap's rule, value per effort, cost first.

### 7.1 Phase 20: read more, refuse less (the reader, both languages)

The cheapest and largest change: the bugs the survey found, and the breadth the builders have. Python: the entry from the
dependency that names the framework when no object is found, with Google's and Railpack's commands (Streamlit, Gradio,
Dash, Panel, Chainlit, Shiny, NiceGUI, Reflex, aiohttp, Sanic, Tornado, Django's ASGI), each with the environment the
platform sets for the host and the port; `python <main file>` as the last rung (D50); `main.py` and `app.py` ranked by
name at any depth; `setup.py`, `setup.cfg`, a Poetry project without a lock, a Pipfile without a lock, `pdm.lock` and
`pylock.toml` locked or read by the platform as `uv.lock` is today; `-r` includes and a `requirements/` folder followed;
`apt.txt`, `Aptfile` and `packages.txt` installed in the platform's Dockerfile (Heroku's and Railpack's convention) and a
build stage with a compiler when the lock holds a source distribution; Django's `collectstatic` at build and `migrate`
offered as `needs.migrate`; the several-candidates refusal replaced by the entry-file ranking the frameworks themselves use,
refusing only on a tie; a root that holds several services names them (and "deploy everything in REPO" onboards each,
D56). Node.js: a literal port becomes `port: N`; `nodemon`, `node-dev`, `pm2` and `forever` are rewritten to `node
<file>`; `main` falls through the entry list the reader already keeps; a stale lockfile is locked again; the lockfile
limit rises to 5 MB; only the entry file and its imports decide the host; dead lines in version files take the lowest
supported line with a note (D48); `.env.<name>.example` is an example. Both: a notebook is a note, never the refusal.

### 7.2 Phase 21: the Node.js items that were "later"

The three items the review of 2026-10-19 ranked 7 to 9, now first-class because the survey shows them in 8 of 15
repositories: pnpm, Yarn and Bun lockfiles installed by their own manager, frozen, scripts off and every entry checked
against the registry as npm's is (OSV-Scanner reads all three); a build stage that installs development dependencies,
runs `build` (or the framework's command), and copies the output into the runtime image without them, with the
frameworks' output paths and start commands of 6.3 built in and `HOST`, `HOSTNAME`, `NITRO_HOST` and `NODE_ENV` set;
TypeScript entries run under type stripping when the project's `tsconfig.json` says `erasableSyntaxOnly`, built with
`tsc` otherwise; workspaces as one service per package with the root lockfile (`npm --workspace`, `pnpm deploy`, `yarn
workspaces focus`, `turbo prune` when `turbo.json` exists). Install scripts stay off, and the reader drafts
`build.scripts` from the platform's own table of packages that need theirs (D53), so the merge approves a named list
instead of an empty one.

### 7.3 Phase 22: run it, then say what to fix

What the builders do with nothing: try the convention, and when the first revision fails, say exactly why. The platform
can do the second half better than any of them, because it already reads the candidate's logs into the release status.
Items: a proxy sidecar on the ingress port for a service bound to loopback with no setting (D51); the platform's images
start under a tiny init so a chained start script runs and still gets `SIGTERM`; a `USER 65532` wrapper stage over a
repository's own image when the contract asks for it, drafted for code nobody reviewed (D52); a static site built and
served behind IAP from the platform's static image (D55); `tests: report` for a suite that cannot run on the platform
(D54); and the diagnosis: Google's documented messages ("failed to start and then listen on the port", "memory limit
exceeded", the probe failures, gunicorn's worker timeout) mapped to the one line the developer changes, and to the
contract key the operator changes when it is the platform's to fix (`port`, `env.HOST`, `resources.memory_mib`).

### 7.4 The decisions

| # | Decision | Default if nothing is said |
|---|---|---|
| D48 | A version file (`.nvmrc`, `.python-version`, `engines`, `requires-python`) that names a line at end of life, for an image the platform builds | The lowest supported line, with a note in the contract and the pull request ("`.nvmrc` asks for 20, at end of life since 2026-04-30; built on 22"); a Dockerfile's own `FROM` stays the developer's and is refused as today |
| D49 | A start the reader cannot rewrite into `node <file>`: a chain (`a && b`), `npm start` with no script, a shell | Run as written under the init of the platform's image, with a note; `nodemon`, `node-dev`, `pm2`, `forever` are rewritten to `node <file>`; `concurrently` and `npm-run-all` stay refused (two processes in one container) |
| D50 | A Python service with no application object the reader knows | Google's and Railpack's rule: the framework or server among the dependencies decides the command (`streamlit run`, `python main.py` with Gradio's variables, `uvicorn main:app`, `gunicorn main:app`, `python -m aiohttp.web`), with the entry file from the frameworks' own discovery lists; as the last rung, `python <main file>` for the first of `main.py`, `app.py`, `server.py`, `run.py`, with `PORT` and `HOST` set and the note that the first revision's log decides; the contract's `build.entrypoint` overrides all of it |
| D51 | A service that binds `127.0.0.1` or `localhost` and reads no variable for it | A proxy sidecar (Nginx, as Google documents it) on the ingress port forwarding to the app's port on loopback, drafted into the contract (`proxy: true`) with its cost note; off for a service that binds every interface; the developer's one line stays the better fix and the contract says so |
| D52 | A Dockerfile of code nobody reviewed whose final image runs as root | The platform adds a wrapper stage (`FROM` the built image, `USER 65532`) when the contract says `build.user: 65532`, which the reader drafts for `trust: unknown`; a reviewer removes it to accept root; an app that writes to a root-owned path fails its first revision with `EACCES`, and the status says to set `env.HOME` or a writable path, or to remove the line |
| D53 | Install scripts for a Node.js service | Still none unless listed; the reader drafts `build.scripts` from the platform's table of packages whose script is needed on Cloud Run (`sharp` below 0.33, `puppeteer`'s download, `node-gyp` builds without prebuilt binaries), each at its locked version, and leaves out those shipping their binaries; the merge approves the list; name-only and `--all` stay refused |
| D54 | Tests of a repository taken as it is that cannot run on the platform (a browser, a database, a seed, Docker) | `tests: report`: run, counted, never a stop; the reader drafts it when `scripts.test` or the pytest configuration names Playwright, Cypress, Selenium, `db:seed`, `docker`, `testcontainers` or a `DATABASE_URL`; `required` otherwise, as today |
| D55 | A front-end site with no server of its own | Built with its `build` script and served from the platform's static image (Caddy, pinned by digest, no package manager) behind IAP with `exposure: lab-members`; `public` stays refused; a site whose `build` needs a secret is refused with the name |
| D56 | A repository root that holds several services | `check_repository` names them (1.20.8); "deploy everything in REPO" or `onboard_application(url, all=true)` opens one contract pull request per service, named after its folder; a root with one service in a folder takes that folder without asking |

What the research says not to do, for this lab: run install scripts because other platforms do (npm 12 stopped, pnpm
and Bun gate them, and the 2025 worms ran from them); serve a placeholder when nothing is found (Oryx hides the
mistake); make `/` the health probe (an API with no root route fails, a sign-in redirect passes); drop the merge as the
review for code nobody reviewed; guess packages from imports (D34 stands: the three repositories without a manifest in
the survey are a person's choice); write any file into the application's repository.

## 8. Limits of this review

The 33 repositories were read, not built: "accepted" means a valid contract, and the count after the changes is a
reading of each repository's refusal list against the decisions, not a run; the live exercise of each phase measures the
real figure on five of them (a Streamlit app, a Next.js app on pnpm, a workspace, a loopback binder, a root Dockerfile).
The sample is small and hand-picked toward templates and well-known applications; a lab's own repositories are messier,
and the two earlier reviews' point stands that no published study measures a platform's hit rate. The proxy sidecar's
share of an instance's bill is not published; it is billed as the app is, only while requests are served, and the
exercise records it. Whether Cloud Run reaches a service bound to IPv6 `::` only is not stated anywhere; Node binds both
by default, so it did not arise. Render's lockfile selection and install-script behaviour, Fly's monorepo support and
CapRover's defaults are undocumented. Nothing from the sampled repositories was executed.

## 10. Appendix: every rule the reader applies today, with its class

Read from `labdeploy/reader.py`, `labdeploy/node.py`, `labdeploy/scaffold.py` and `labdeploy/dockerpolicy.py` at 1.21.0.
**Inherent**: the container needs it and no platform can take it over. **Platform**: a flag, a setting in the contract,
a lock, a wrapper, a sidecar or a wider ladder takes it over with nothing added to the repository. **Policy**: the lab's
rule, kept on purpose, with its cost. **Guess**: a refusal between equals, which stays. **Bug**: wrong today.
