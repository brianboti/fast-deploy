# Refactoring plan: a provider-independent Cloud Infrastructure MCP (2026-10-28)

This document is the analysis that precedes the code. It answers seven questions in order: what the repository does today,
where application and infrastructure responsibilities are mixed, the architecture the refactor moves to, the MCP catalog it
exposes, which files stay, change, move or are new, the request and response contract, and how the Google Cloud adapter
implements the provider interface. The implementation follows the plan incrementally; nothing that works today is deleted.

## 1. Current architecture

Fast Deploy (`labdeploy`, 1.34.0, about 33,000 lines of Python) is a release controller for Python and Node.js web services
on Google Cloud Run. Claude calls its MCP tools; the controller decides what is allowed; GitHub Actions does the work.

```
Claude (release manager)
  │  28 MCP tools (labdeploy/server.py), OAuth 2.1 or bearer tokens (labdeploy/oauth.py)
  ▼
labdeploy.controller.Controller  ── SQLite (plans, audit events, onboarding, operations ledger)
  │
  ├─ GitHub App (labdeploy/github.py): read platform.yaml, open pull requests, dispatch and watch workflows
  ├─ Repository analysis and drafting (analyzer, reader, scaffold, node, contract, dockerpolicy, workflows)
  ├─ Terraform roots rendered per application (labdeploy/infra.py → infra/gcp/apps/<service>), applied by the pipeline
  ├─ Cost model for Cloud Run (labdeploy/cost.py), measured right-sizing (rightsize, telemetry)
  └─ Read-only cloud views (labdeploy/cloud.py Observer): Cloud Run, Monitoring, Logging, Artifact Analysis
  ▼
GitHub Actions (templates/deploy-gcp.yml): tests → audit → build → scan → sign → push → deploy → probe → promote → bake
  ▼
Google Cloud: Cloud Run, Artifact Registry, Cloud SQL / Firestore / buckets / topics declared under `needs`
```

What each part is, classified by the layer it belongs to:

| Area | Modules | Layer today |
|---|---|---|
| MCP server, auth, rate limits, audit | `server.py`, `oauth.py`, `toolpin.py`, `settings*.py` | Shared transport, coupled to the release controller |
| Release workflow | `controller.py`, `release.py`, `promotion.py`, `bake.py`, `journal.py`, `recovery_supervisor.py`, `status.py`, `journey.py`, `deployments.py`, `deployment_page.py`, `aftercare.py`, `updates.py`, `scheduler.py`, `operations.py` | Application delivery |
| Repository knowledge and drafting | `analyzer.py`, `reader.py`, `scaffold.py`, `node.py`, `contract.py`, `contractcheck.py`, `onboarding.py`, `workflows.py`, `dockerpolicy.py`, `pins.py`, `resolver.py`, `resolution_protocol.py`, `workers/resolver` | Application delivery |
| Build supply chain | `provenance.py`, `attest.py`, `scan.py`, `sbom.py`, `leaks.py`, `datafiles.py`, `secret_admission.py`, `jobimages.py` | Application delivery (runs on the GitHub runner) |
| GitHub integration | `github.py`, `connections.py`, `connections_page.py`, `.github/workflows/*`, `templates/*` | Application delivery |
| Application jobs | `jobs.py`, `jobbroker.py` | Application delivery |
| Cloud reads and monitoring | `cloud.py` (Observer, GoogleToken), `telemetry.py`, `monitor.py`, `charts.py` | Infrastructure (read side), shaped for Cloud Run |
| Infrastructure as pull requests | `infra.py`, `infra/gcp/modules/*`, `infra/gcp/project` | Infrastructure, driven by an application's `platform.yaml` |

The existing MCP catalog has no primitive infrastructure tool. Infrastructure is reached only through an application:
`propose_infrastructure(application)` renders a Terraform root from that application's reviewed `platform.yaml` and opens a
pull request. There is no way to ask for a virtual machine, a disk, a network or a database without a repository.

## 2. Problems: where the layers are mixed

1. **Infrastructure needs an application.** Every infrastructure path starts from a registered GitHub repository and its
   `platform.yaml`. The `Needs` model (buckets, topics, database) lives inside `AppSpec`; the Terraform root takes the
   service name, the repository ids and the workflow path as inputs. "Give me three Linux VMs and a database" cannot be said.
2. **One tool does everything.** `onboard_application` and `deploy_latest` combine repository analysis, pull requests,
   workflow dispatch, build, test, scan, sign, deploy, probe, promote and bake. This is the `deploy_github_repo_to_google_cloud`
   shape the requirements name as too much responsibility for an infrastructure layer.
3. **GitHub access is a precondition of the server.** `build_app` constructs `GitHub.from_config` before anything else; the
   server cannot start as an infrastructure service without a GitHub App or token.
4. **Google Cloud specifics are not behind an interface.** Cloud Run, Monitoring, Logging, Artifact Analysis and Cloud SQL
   are called by name from `cloud.py`, `controller.py`, `telemetry.py`, `cost.py`, `infra.py` and the Terraform modules.
   `create_deployment_plan(cloud="gcp")` accepts the parameter and refuses every other value by policy; no adapter exists.
5. **Application decisions are made by the platform.** Scaling (instances, concurrency), clustering (none), sessions
   (stateless only), request timeouts, the health path and the release cadence are decided or constrained by `enforce()` in
   `models.py`. These are application-layer decisions that an infrastructure service must not make.
6. **The cloud identity is bound to the pipeline.** The controller holds no cloud credential by design; the deployer identity
   exists on the GitHub runner. An infrastructure service must hold its own, least-privilege provider credential.
7. **Configuration mixes both layers.** `Config.applications` (repositories, branches, workflows) sits next to `principals`,
   rate limits and allowed hosts.

What is already right and is kept: bearer principals stored as hashes, per-identity and per-address rate limits, every tool
audited with identity, outcome and duration, safety annotations on every tool, structured outputs, structured error
sentences, the strict argument check (`StrictMCP`), the metadata-server-or-gcloud token acquisition (`GoogleToken`), the
read-only Monitoring queries, list-price cost estimation with an explicit verification date, and labels on every resource.

## 3. Proposed architecture

Two layers in one repository, two packages, two servers, one direction of dependency.

```
Application Layer (any system: Claude, a CI job, another service, the existing Fast Deploy workflow)
  │
  │  Infrastructure contract: InfrastructureRequest → InfrastructureResponse (provider-neutral, typed)
  ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  cloudinfra — Cloud Infrastructure MCP                                   │
│                                                                          │
│  mcp/server.py        FastAPI + StrictMCP: bearer auth, rate limits,     │
│                       audit, safety hints, structured errors             │
│  mcp/catalog.py       The service catalog: one record per tool          │
│  mcp/tools/*          compute, storage, network, database,               │
│                       infrastructure, operations                        │
│  orchestration/       validator → planner → provisioner (and destroy)    │
│  state/               SQLite: requests, resources, operations, events    │
│  security/            principals, token hashes, request validation       │
│  observability/       structured JSON log lines with request ids         │
│  providers/base.py    CloudProvider: the primitive interface             │
└──────────────────────────────┬───────────────────────────────────────────┘
                               │  CloudProvider
              ┌────────────────┼──────────────────┬──────────────────┐
              ▼                ▼                   ▼                  ▼
   providers/gcp/        (AWSProvider)       (AzureProvider)   (JetstreamProvider)
   auth, api, translate,   later               later              later
   compute, storage,
   network, database,
   monitoring, pricing
              │  REST: compute.googleapis.com, sqladmin.googleapis.com,
              │        storage.googleapis.com, monitoring.googleapis.com
              ▼
        Google Cloud
```

The existing package `labdeploy` stays and becomes the optional **application delivery workflow**: it owns repositories,
builds, tests, images, releases, promotion and the Cloud Run specifics. It may import `cloudinfra`; `cloudinfra` never
imports `labdeploy`, `github`, `templates` or anything that reads a repository. A test enforces the direction.

| Layer | Owns |
|---|---|
| Application | source code, tests, builds, Docker images and other artifacts, release decisions and versions, scaling and clustering behaviour, sessions, application configuration, the GitHub workflow |
| Infrastructure (`cloudinfra`) | compute, network, storage and managed database provisioning; resource lifecycle (validate, plan, provision, query, destroy); infrastructure status, health and usage; cost estimates and limits; provider abstraction; provider authentication; cleanup of what it created |

Decisions and their reasons:

- **A second package, not a rewrite of the first.** Moving 33,000 lines into `src/` would change every import, the
  Dockerfile, the workflow templates and the scripts for no functional gain. The boundary is enforced by a test, the two
  servers are separate processes with separate principals and credentials, and the direction of dependency is one-way.
- **Provider REST APIs, not Terraform, for the primitives.** The existing Terraform roots are shaped for Cloud Run
  services and applied by the GitHub pipeline from merged pull requests; they remain the application workflow's mechanism.
  The infrastructure core calls the Compute Engine, Cloud SQL Admin, Cloud Storage and Monitoring APIs through one thin
  client (`providers/gcp/api.py`), the same way `labdeploy/cloud.py` already does. That keeps the unit tests free of a
  Terraform binary, state buckets and provider plugins, makes every provider call mockable, and lets the planner compute a
  plan offline. A Terraform-backed driver can sit behind the same `CloudProvider` interface later.
- **The provider project is operator configuration, never a request parameter.** The Application Layer chooses the provider
  name and the region; the operator's `config` names the project, the allowed regions, the limits and the credentials.
- **Asynchronous provisioning.** A Cloud SQL instance takes minutes. `provision_infrastructure` validates, plans, records the
  request and starts provisioning in a bounded worker; it returns at once with `PROVISIONING` and an operation id, or waits
  up to 45 seconds when asked. `get_infrastructure_status` reads the provider for the live state.
- **Failure cleans up.** When one resource of a request fails, the provisioner deletes the resources it created for that
  request, records each deletion, and reports `FAILED` with the error and the cleanup outcome. Nothing is left behind
  silently; what could not be deleted is named.
- **No command execution through parameters.** Requests carry sizes, names, versions and switches, never a startup script,
  an SSH key, a shell command or a provider-specific structure. Access to a virtual machine is through OS Login (IAM).

## 4. MCP catalog

Twenty-seven tools in six groups. Each primitive creates or acts on a record with a request id, so a resource made by
`create_compute` is as traceable and destroyable as one made by `provision_infrastructure`.

| Group | Tool | Purpose | Safety hint |
|---|---|---|---|
| Compute | `create_compute` | Virtual machines: count, cpu, memory, os, boot disk, public address | changes cloud |
| | `get_compute` | One instance's live state, addresses and attached disks | read-only |
| | `list_compute` | Instances this service created, from the provider, filtered by request or owner | read-only |
| | `resize_compute` | Change cpu and memory (stop, resize, start) | changes cloud |
| | `delete_compute` | Delete one instance | destructive |
| Storage | `create_storage` | Persistent disks (block) or an object bucket | changes cloud |
| | `attach_storage` | Attach a disk to an instance | changes cloud |
| | `get_storage` | One disk's or bucket's state | read-only |
| | `delete_storage` | Delete one disk or an empty bucket | destructive |
| Network | `create_network` | A private network with one subnet in the region and the firewall rules the request implies | changes cloud |
| | `get_network` | A network's subnet, rules and the instances in it | read-only |
| | `configure_firewall` | Add an ingress rule (ports, sources) to a network this service created | changes cloud |
| | `delete_network` | Delete rules, subnet and network | destructive |
| Database | `create_database` | A managed PostgreSQL or MySQL instance with one database and one user | changes cloud |
| | `get_database` | Host, port, state, version, storage, backups | read-only |
| | `delete_database` | Turn deletion protection off and delete | destructive |
| Orchestration | `validate_infrastructure_request` | Validate a full request against the contract, the provider and the limits; nothing is created | read-only |
| | `plan_infrastructure` | The resources a request would create, their provider mapping, names and estimated monthly cost | read-only |
| | `provision_infrastructure` | Validate, plan, record and provision a full request | changes cloud |
| | `get_infrastructure_status` | A request's status, resources, endpoints and operations, refreshed from the provider | read-only |
| | `list_infrastructure` | Requests this caller may see | read-only |
| | `destroy_infrastructure` | Delete everything a request created, in reverse order | destructive |
| Operations | `get_resource_health` | Provider state and readiness of one resource | read-only |
| | `get_resource_usage` | CPU, memory and disk utilisation from Cloud Monitoring | read-only |
| | `get_resource_cost` | Estimated monthly cost of a request or resource from list prices | read-only |
| | `get_operation` | One operation's status, timing and error | read-only |
| | `get_service_status` | Version, providers, allowed regions, limits, operation lanes | read-only |

Left out on purpose: `create_subnet` (every network gets one subnet in the request's region; a second subnet is a later
feature, not a first catalog item), `get_database_status` (`get_database` carries the state), and any tool that takes a
repository, an image or a command.

## 6. Request and response contract

```yaml
# InfrastructureRequest (every block optional; at least one of compute, storage, network, database)
provider: gcp                 # the adapter; unknown names are refused with UNSUPPORTED_PROVIDER
region: us-central1           # must be in the operator's allowed regions
zone: us-central1-a           # optional; the provider picks the region's first zone
name: analytics               # optional prefix of every resource name; else infra-<8 hex>
labels: {team: data}          # optional, applied to every resource with the service's own labels
compute:
  count: 2                    # 1 to limits.max_instances
  cpu: 4
  memory_gb: 16
  os: ubuntu                  # ubuntu | debian | rocky (a family; the provider picks the current LTS image)
  boot_disk_gb: 20
  public_ip: false            # true also needs network.public_access or an existing network that allows it
storage:
  type: persistent            # persistent (one block disk per instance, or one disk alone) | object (a bucket)
  size_gb: 200
database:
  engine: postgresql          # postgresql | mysql
  version: "16"               # optional; the provider's default when omitted
  size: small                 # small | medium | large (the provider maps the tier)
  storage_gb: 10
  high_availability: false
  public_access: false        # false: private address on the request's network
  database_name: app
  username: app
network:
  public_access: true         # public addresses allowed, ingress rule for allowed_ports from allowed_sources
  cidr: 10.10.0.0/24
  allowed_ports: [80, 443]
  allowed_sources: ["0.0.0.0/0"]
  iap_ssh: true               # port 22 from Google's IAP range only; no SSH from the internet
```

## 7. Provider abstraction

```python
class CloudProvider(ABC):
    name: str                                    # "gcp"
    def regions(self) -> list[str]
    def zones(self, region) -> list[str]
    def validate(self, request) -> list[Problem]     # provider-specific shape checks; the validator adds the generic ones
    def plan(self, request, names) -> list[PlannedResource]   # pure translation, no network call
    def estimate_cost(self, planned) -> CostEstimate
    def quota(self, region) -> dict[str, Quota]      # best effort; the provisioner checks headroom before creating
    def create_network(self, spec, ctx) -> NetworkResource
    def configure_firewall(self, network, rule, ctx) -> FirewallRule
    def get_network(self, resource) -> NetworkResource
    def delete_network(self, resource, ctx) -> None
    def create_storage(self, spec, ctx) -> StorageResource
    def attach_storage(self, storage, compute, ctx) -> StorageResource
    def get_storage(self, resource) -> StorageResource
    def delete_storage(self, resource, ctx) -> None
    def create_compute(self, spec, ctx) -> ComputeResource
    def get_compute(self, resource) -> ComputeResource
    def list_compute(self, labels) -> list[ComputeResource]
    def resize_compute(self, resource, cpu, memory_gb, ctx) -> ComputeResource
    def delete_compute(self, resource, ctx) -> None
    def create_database(self, spec, ctx) -> tuple[DatabaseResource, Credentials]
    def get_database(self, resource) -> DatabaseResource
    def delete_database(self, resource, ctx) -> None
    def resource_status(self, resource) -> ResourceStatus
    def resource_health(self, resource) -> Health
    def resource_usage(self, resource, minutes) -> Usage
```

`provision_infrastructure` and `destroy_infrastructure` are not provider methods: the orchestrator owns the order (network,
storage, compute, database; the reverse to destroy), the state, the cleanup on failure and the audit trail, so every
provider implements only primitives and gets the lifecycle for free.

`GCPProvider` translates:

| Generic | Google Cloud |
|---|---|
| `cpu`, `memory_gb` | `e2-standard-N` (4 GB per vCPU), `e2-highmem-N` (8), `e2-highcpu-N` (1), else `e2-custom-C-M` within E2's ratio |
| `os: ubuntu` | `projects/ubuntu-os-cloud/global/images/family/ubuntu-2404-lts-amd64` |
| `storage.type: persistent` | `pd-balanced` disk in the instance's zone, `attachDisk` after the instance exists |
| `storage.type: object` | A bucket with uniform access and public access prevention enforced |
| `network` | VPC with `autoCreateSubnetworks=false`, one subnet with the CIDR, firewall rules: internal, IAP SSH, public ingress |
| `database.engine: postgresql, size: small` | Cloud SQL `POSTGRES_16`, tier `db-f1-micro` (medium `db-custom-2-7680`, large `db-custom-4-15360`), private address through Private Services Access, deletion protection on, automated backups on |
| `public_ip: true` | One `ONE_TO_ONE_NAT` access config on the instance |
| every resource | labels `managed-by=cloudinfra`, `cloudinfra-request=<id>`, `cloudinfra-owner=<principal>` and the request's own |

Adding AWS later means `providers/aws/` implementing the same methods and one line in the registry; no change to the
models, the orchestrator, the state, the server, the catalog or the Application Layer.

## Tests at the boundary

Unit tests (no cloud): request validation and every error code; provider selection and `UNSUPPORTED_PROVIDER`; generic
request to Google Cloud translation; planned names and cost; provisioning order; a failure in the middle and the cleanup it
triggers; destroy in reverse; status refresh; the MCP server end to end (initialize, list, call) with a fake provider API;
the catalog document matching the registered tools; the import boundary; and the design test: one Ubuntu VM with 4 CPUs and
16 GB from a request that names no repository, image, workflow or application. Integration tests against a real project run
only when `CLOUDINFRA_INTEGRATION=1` and are marked so.
