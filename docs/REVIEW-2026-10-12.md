# Strict review of Lab Deploy 1.4.2 (2026-10-12)

Scope: every file under `labdeploy/`, `infra/`, `.github/workflows/`, `templates/`, the documents, the operator scripts, and the live state of the staging project and the two GitHub repositories. Four reviewers read the code in parallel (control plane, release runner and cost model, Terraform and pipelines, documentation and operations); every finding below was then verified against the file, the installed libraries or the live system before it was kept. Nothing was changed. Baseline: 224 tests pass, ruff and zizmor clean, both Terraform roots validate.

Official documents read for this review, beyond those in `docs/SOURCES.md`: the MCP authorization specification (2025-11-25), the `gcloud run jobs update` reference, Google's Workload Identity Federation guide for deployment pipelines, Google's IAM roles overview and Cloud Storage IAM roles, the Eventarc retry policy, the programmatic budget notifications reference, the Cloud Run services list reference, Firestore, Cloud Run, Cloud Storage, Pub/Sub and Cloud SQL pricing pages, Google's Terraform security page, GitHub's environment and OIDC documentation, and the uvicorn proxy-header behaviour in the installed version.

## Verdict in one paragraph

The platform does what it claims and proves it: every feature was exercised live, failures are reported honestly, data is never destroyed by an automated step, and the supply chain (pinned actions, hashed dependencies, signed images, federated identities) follows current practice. It is not production grade yet, and two of today's additions carry defects that would hit the first real application with database migrations. The most serious gap is one of trust rather than code: the pipeline's "merge means apply" promise is not enforced by GitHub, so a direct push to `main` applies infrastructure with a project-wide IAM administrator identity. The fixes are days of work, not weeks, and are listed in order at the end.

## Findings, most severe first

Severity reflects impact on this lab's staging use. "Verified" means a reviewer's claim was reproduced by reading the exact lines, the installed library, the vendor's page or the live system.

### High

1. **Merging is not the gate it is documented to be** (verified live). `brianboti/lab-deploy` has no branch protection and no rulesets; the `infra` environment has only a branch policy. The apply identity's federation binding (`infra/gcp/modules/project/pipeline.tf:49`) trusts any job that runs in that environment, with no condition on the branch or the workflow file, unlike the app deployer's binding (`infra/gcp/modules/service/main.tf:204`). The identity holds `roles/editor` and `roles/resourcemanager.projectIamAdmin` (`pipeline.tf:69-71`). Anyone who can push to `main` can therefore change the project's IAM through the pipeline without a review. Today that is the operator and this assistant; the controller's own GitHub token could not write (its workflow-update attempt failed for lack of write access), but the design must not depend on that. Fix: protect `main` (pull request required, one review, CODEOWNERS for `infra/`, `labdeploy/infra.py` and `.github/workflows/`), forbid bypass on the `infra` environment, and add `assertion.ref == 'refs/heads/main' && assertion.workflow_ref == 'brianboti/lab-deploy/.github/workflows/infra-apply.yml@refs/heads/main'` to the apply binding, as Google's deployment-pipeline guide shows.

2. **The plan policy is a lint, not a guard** (verified by reading `labdeploy/infra.py:199-233`). It refuses only `roles/owner` and `roles/editor` on project bindings, so a root may grant `roles/resourcemanager.projectIamAdmin`, `roles/iam.serviceAccountTokenCreator` or `roles/secretmanager.admin`; it never rejects `allUsers` or `allAuthenticatedUsers` on any IAM resource; it inspects `member`, `members` and `account_id` but not `service_account_id`, so a binding on the platform's own apply identity passes; authoritative `*_iam_policy` resources are not inspected; the region rule ignores Firestore's `location_id`; the bucket, database and label rules run only on `create`, so an update that turns public access prevention off passes; unknown values (`after_unknown`) are never treated as violations. The checker also runs from the pull request's own checkout (`.github/workflows/infra-plan.yml:81`), so a change to the rules and a root in the same pull request grades itself. Fix: deny public members everywhere, use an allow-list of roles an application root may grant, match the platform's identities in every identity-bearing field including `service_account_id` and parsed policy data, apply the invariants on update and replace, treat unknown values as violations, and run the checker from a pinned platform ref.

3. **Every tool call blocks the whole controller** (verified in the installed library: `mcp/server/fastmcp/utilities/func_metadata.py:112-115` calls synchronous tools inline on the event loop; all tools in `labdeploy/server.py` are synchronous; `labdeploy/controller.py:777` sleeps in the status wait loop). One `get_deployment_status` with `wait_seconds` stalls health checks, sign-in refreshes and every other caller for up to 45 seconds; `get_service_health` and the GitHub calls behave the same. With one operator this is rarely visible; with the lab it will be. Fix: make the tools `async` and run controller work through a thread pool, with an asynchronous sleep in the wait loop.

4. **A runner lost during a migration wedges the service** (verified: `labdeploy/release.py:296` lists the recoverable checkpoint states and `migrating`, written at line 410, is not among them; `labdeploy/status.py:140` has the same gap). The deploy job has a twenty-minute limit and a migration may run fifteen; after a cancellation there, every recovery run and every later release raise "Unknown recovery journal state; manual review required" until someone edits the checkpoint object by hand, and the controller says nothing changed although a schema change may have half-run. Fix: add `migrating` to the recoverable states (traffic restoration is a no-op there), record the job execution name in the checkpoint before executing, and extend the advice.

5. **A one-word migration command can never release** (verified: `gcloud run jobs update` has `--clear-env-vars`, `--clear-labels`, `--clear-network`, `--clear-secrets`, `--clear-volumes` and others, but no `--clear-args`; `labdeploy/release.py:101` passes it). `migrate: ["./migrate.sh"]` fails at the `migrating` phase on every attempt, fail-closed. The live trial used a three-part command and never hit it. Fix: pass `--args=""`, which the reference documents as the reset.

6. **The spending cap is brittle exactly when it matters** (verified by reading `cap-workflow.yaml` and the vendor pages the reviewer cited). The workflow has no retry and no error handling around the per-service and per-instance calls, Eventarc does not retry a failed execution, and no alert policy watches workflow failures: one 403 on one service stops the loop and every later service stays open, silently, on every notification. Separately, Google's `alertThresholdExceeded` is the highest configured budget rule reached, and the rules are 0.5, 0.9 and 1.0 (`modules/project/main.tf:78-87`), so `detach_threshold = 1.2` can never fire and any `threshold` other than those three rounds down unseen. Notifications also repeat several times a day all month, so a service an operator reopened is closed again at the next one, while a later Terraform apply reopens a capped service because `ingress` is not in the service's `ignore_changes`. Fix: wrap each call in a retry and a try block that records failures and continues, add an alert on failed workflow executions, compute the ratio from `costAmount` and `budgetAmount`, and decide one semantics for a lifted cap (a marker label the workflow honours, and `ingress` either ignored or refused while capped).

### Medium

7. **A dispatch GitHub never confirmed is reported as in progress forever** (verified: `labdeploy/controller.py:782-786` overwrites the plan state with the workflow summary, which returns `awaiting_workflow` when no run is visible, so the advice for `dispatch_unknown` in `labdeploy/status.py:121` is unreachable). After a timeout at dispatch the operator is told to ask again indefinitely. Fix: a distinct non-terminal state when the dispatch state is unknown or the plan has expired without a visible run.

8. **Auto-deploy stops after one transient failure** (verified: `labdeploy/controller.py:179-182` skips a commit whenever any plan exists for it, in any state). A GitHub error after the plan is stored leaves it `planned` and the commit is never retried until a new one lands; the only trace is one audit event. Fix: retry expired or errored attempts with a capped backoff.

9. **The Firestore cost note is wrong, in the direction that matters** (verified on Google's pricing page: "No free quota for named databases"; regional storage is $0.000205479 per GiB-hour, about 0.15 per GiB-month, not the 0.18 multi-region figure in `labdeploy/cost.py:68`). The platform creates a named database per application (`modules/service/needs.tf:80`), so the free-quota line in every estimate and in `docs/SETUP.md` describes a quota these apps never get. All other prices in `cost.py` match the current pages.

10. **Migration timeouts disagree** (verified: `labdeploy/release.py:17` runs every command with a 600-second limit while the job is given `--task-timeout=900` at line 97, and a `TimeoutExpired` is not caught at line 107). A ten-to-fifteen-minute migration makes the release record `traffic_restored` with a bare exception while the job keeps running, and a retry starts a second migration beside it. Fix: one constant, and on timeout record the execution and refuse new releases until it ends.

11. **The cost ceiling is a compute bound only** (verified: `labdeploy/cost.py:105,118` and `labdeploy/controller.py:584-597`). Request fees, egress and the per-image scan are outside the number compared with the operator's ceiling; and the weekly report clamps a drifted live `maxScale` to 5 before pricing it (`cost.py:285-296`), so a service drifted to 100 instances is priced as 5 while the drift line says 100. Fix: name it a compute bound in the policy text, add a request term from a declared request budget, and never clamp live settings when pricing them.

12. **SQLite is used without a write-ahead log and with read-modify-write races** (reviewer finding, plausible from `labdeploy/controller.py:33-41, 826-828` and `labdeploy/oauth.py:119-121`): the scheduler thread, thread-pool REST handlers and the event loop all write; two concurrent status calls can both record an outcome, and `persist` can overwrite a newer payload. The unauthenticated `/register` and `/authorize` endpoints add rows that are pruned only when a registration happens. Fix: WAL mode, state-guarded updates, `DELETE ... RETURNING` for codes, a scheduled prune.

13. **Client secrets and sign-in capabilities land in clear text** (verified: the registered Claude clients use `client_secret_post`, and `oauth_clients.payload` holds the secret verbatim; `labdeploy/server.py:34,80` writes `uvicorn.access` at INFO into the rotating log, where `/login?request=<id>` and `/authorize?...` lines appear). Impact is low because a secret alone yields no token and a request id still needs the operator token, but the docstring's "secrets are stored only as hashes" is not true. Fix: force public clients or hash the secret; drop the access logger or strip query strings.

14. **Pipeline identities are broader than their jobs** (verified roles in `pipeline.tf:53-73`). The plan identity has the basic `roles/viewer` plus read access to every state object, including the foundation's; the apply identity has `roles/editor` on top of nine administrative roles and project-wide `storage.admin`, which reaches application data and the foundation's state. Google's guidance is to avoid basic roles in production. Fix: enumerate the predefined roles the service module needs, scope state access per prefix, and add `event_name` and `workflow_ref` conditions to the plan binding.

15. **Policy evasion through the generated root** (verified: `labdeploy/infra.py:58-63` writes values with JSON quoting, so a `migrate` part containing `${...}` becomes a live interpolation in `main.tf`, and `models.py:43` allows `$`, `{` and `}`). Fix: escape `${` and `%{` in the renderer and reject `$` and `^` in migrate parts.

16. **The entry documents deny features that exist** (verified). `README.md:51,56,168` and `docs/ARCHITECTURE.md:82-83` say databases are not provisioned, there is no automated infrastructure application and no hard spending cap; `PROJECT_HANDOFF.md:140,342,435,448,491` still says "Continue from 0.9.2", tells a successor to run the state migration again, and lists database provisioning as planned. `docs/SETUP.md:217,253` point at Terraform variables that moved into `applications.<app>.infra`, and the first-app bootstrap order asks for a rendered root before the target values exist. There is no license file in a public repository, no release tag for any version, `.github/dependabot.yml:10-11` watches a Terraform directory that no longer holds roots, and CI runs only on push, so no scheduled dependency audit ever runs.

17. **Disaster recovery exists only for the database file** (verified). The nightly copy stays on the same disk; `config.local.yaml`, the operator token hash and the operator scripts in `~/.local/share/lab-deploy/` are backed up nowhere and the scripts are not in the repository; a restore has never been rehearsed; there is no runbook for a lost or sleeping laptop. Alert delivery, the notification webhook and the cap have never been exercised end to end, and no owner, SLO or escalation is written down.

18. **Behind a proxy on the container path the per-address limits collapse** (reviewer finding, plausible: the Dockerfile starts uvicorn on `0.0.0.0` without `--forwarded-allow-ips`, and the installed uvicorn trusts forwarded headers only from loopback). Verified not to affect the laptop path: a request through the ngrok tunnel was recorded with the real client address.

## Against the criteria

- **Works properly.** Yes for everything exercised: releases, rollback, cancel, redeploy, auto-deploy, needs, migrations, the pipeline. Two defects in today's 1.4.0 (findings 4 and 5) and the cap's fragility (6) would surface on the first real application with migrations or a budget event. Fix before onboarding.
- **Best practices.** Largely yes: federated identities with immutable ids, no keys, hashed tokens, pinned actions and locked dependencies, signed images verified before release, fail-before-mutate checkpoints, data never destroyed automatically, per-root state. Exceptions: the unenforced review gate (1), the policy's reach (2), the identities' breadth (14).
- **Fast.** Adequate for one operator and the five-minute auto-deploy loop. Not for several people at once: one waiting call blocks every other (3), and the first tool Claude calls makes about seven GitHub requests per application.
- **Trustable.** The evidence discipline is unusually good: every claim in the validation record was produced live, and failures are reported as what they are. The one trust claim that is not true today is "merging applies exactly this plan" as the only path.
- **Modern.** Yes: the 2025-11 MCP authorization profile, OIDC federation, SLSA attestations, policy over plans, Score-style declared needs.
- **Production grade.** Not yet, by design and by gaps: single region, zonal database, no cross-region copies, no organisation policies, no data-access audit logs, the controller on a laptop with a free tunnel, no license, no release process, no rehearsed restore, no on-call or SLO, and findings 1 to 6.

## What is strong

Honest status reporting with a durable checkpoint and an independent recovery workflow; traffic decisions judged by observed routing, not exit codes; least-privilege runtime identities with name-conditioned grants for secrets and Firestore; exact argument lists with validated identifiers for every subprocess; a validation record that separates unit, mocked and live evidence; hash-locked dependencies and commit-pinned actions with a consistency test; private-only Cloud SQL with IAM sign-in; a pipeline that refused twice today exactly when it should have.
