# A repository as it is, and a production tier: Fast Deploy 1.14.1 against research and practice

Written 2026-10-16 as a read-only review. Nothing in the code was changed; the plan it produces is in `docs/ROADMAP.md`
(Phases 13 to 17, decisions D31 to D40). Two questions were asked: how to take a messy repository as it is and deploy it
safely without changing it; and what "production level" means for this platform, as a plan.

Method: the platform's documents, code and validation records were read (version 1.14.1, commit 26d8079; 478 tests pass;
23 tools). Seven themed literature and practice searches then ran in parallel (deploy-from-source platforms and their
open-source detection rules; configuration kept outside the repository; safety of building and running unknown code;
reading a messy Python repository and the research on automated environment setup; production delivery and reliability
on Cloud Run with the deployment-safety literature; production security and compliance, HIPAA on Google Cloud, supply
chain and MCP security; the controller itself in production), each returning only sources it had fetched or seen in
search results, about 300 in all. The load-bearing claims were then checked again directly; section 9 marks each source
as fetched, seen only in a search result, or unverified. Prices are a special case: Google's commercial pricing pages are
script-rendered and truncate for an automated reader, so every price below was read from the **Cloud Billing Catalog
API** on 2026-10-16 (the authoritative list, effective that day) for `us-central1` or global, and cross-checked against
the pages the searches managed to read; Google's convention of 730 hours a month is used, and the lab's credits are not
counted. Two limits to keep in mind: platform engineering has little peer-reviewed evidence, so several judgements rest
on official documents and primary engineering sources; and the automated-setup research measures benchmarks, not this
lab's repositories.

Acronyms: BAA (business associate agreement, the HIPAA contract with a cloud provider), CMEK (customer-managed encryption
keys), CIMD (client ID metadata document, the newer OAuth client registration for MCP), DCR (dynamic client registration),
IAP (Identity-Aware Proxy), MCP (Model Context Protocol), OIDC (OpenID Connect, the identity token GitHub Actions
presents to Google), PHI (protected health information), PITR (point-in-time recovery), SBOM (software bill of
materials), SCC (Security Command Center), SLA (service-level agreement), SLO (service-level objective), SLSA (the
build-provenance standard), WIF (Workload Identity Federation), VPC-SC (VPC Service Controls).

## 3. What the evidence is, and what does not exist

The strong sources are of four kinds: official product documents and the Billing Catalog (product facts and prices);
standards and regulations (SLSA 1.2, NIST SP 800-190 and 800-66r2, the HIPAA Security Rule and its January 2025
proposed update, the MCP specification through its 2026-07-28 revision, PEP 751); peer-reviewed studies of why systems

directly, which is better evidence of what a platform does than its documentation.

What does not exist: a peer-reviewed comparison of buildpack and Dockerfile cold starts for Python on Cloud Run (Google
states image size does not matter; the lab measured 203 MB against 53 MB); a benchmark that isolates "a web app with a
Dockerfile" from the general environment-setup problem, so the agents' success rates do not transfer to the lab's
repositories; a published cost comparison of a free VM against a Cloud Run minimum instance for a tiny control plane;
and a HIPAA certification of any cloud, which HHS does not offer.

## 4. Question 1: a repository as it is

### 4.1 What "as it is" has to mean

Today a repository must carry three things *in its files* (a `Dockerfile` or `Procfile`; `platform.yaml` with `reviewed:
true`; `requirements.txt`, a hash-locked `requirements.lock`, tests and a health path) and three things *in GitHub* (the
three release workflows pinned to a platform commit; a `staging` environment with nine variables; branch protection).
Everything the checker drafts goes into the repository through a pull request, and nothing deploys until a person merges
it. So "take the repository as it is" means moving all six out of the repository and into the platform's own records,
while keeping what the design is built on: a reviewed contract tied to an exact commit, a build that proves which commit
it built, and a human merge before anything changes in the cloud.

The evidence says that is possible for all six, with one trade-off that must be decided deliberately (section 4.3): once
the pipeline runs from the platform's repository instead of the app's, the platform's repository becomes the one place
whose compromise reaches every app's identity.

### 4.2 What the platforms that "deploy from source" actually do

Every hosted platform that takes a repository as it is relies on detection rules plus platform-side settings, and only
one of them writes into the user's repository (`fly launch` writes `fly.toml` and a Dockerfile, and asks before
overwriting). Their rules are public and consistent enough to borrow:

- **Google's buildpacks** (the path Fast Deploy already uses for a `Procfile`) need no requirements file at all: Python
  is detected by any `.py` file; `requirements.txt` wins over `pyproject.toml`, then `poetry.lock` or `uv.lock` pick the
  package manager (`pyproject.toml` support became GA on 2026-01-13); the Python version comes from `GOOGLE_PYTHON_VERSION`,
  then `.python-version`, then the builder's default (3.13 on the Ubuntu 22.04 builder, 3.14 on 24.04; `runtime.txt` is
  never read); the entrypoint comes from `GOOGLE_ENTRYPOINT`, then a `Procfile` (`web` mandatory), then `main.py`/`app.py`
  as `gunicorn -b :8080 main:app`, and on Python 3.13 and later from the server listed in the requirements (gunicorn,
  uvicorn, `fastapi[standard]`, gradio, streamlit); with nothing found the build fails with an exact message rather than
  guessing. Every one of those inputs can be passed as a build environment variable from outside the repository.
- **Heroku's** Python buildpack registers no default web process, so a `Procfile` is effectively required; since
  2025-12-10 it refuses a repository that holds more than one package-manager file instead of guessing.
- **Railway's Railpack and Nixpacks** (open source) use a start-command ladder (Django by `manage.py` and
  `WSGI_APPLICATION`, FastAPI by `uvicorn main:app`, Flask by `gunicorn main:app`, else `python <file>`), and emit a
  server command only when that server is a declared dependency; Railpack takes its whole configuration from an
  environment variable (`RAILPACK_CONFIG_FILE`) pointing at a file anywhere.
- **Microsoft's Oryx** (Azure, open source) recognises `requirements.txt`, `pyproject.toml`, `setup.py`, `uv.lock`,
  conda files and notebooks, finds Django by a `wsgi.py` in a subfolder and Flask/FastAPI by file names holding an
  `app` object, and, when it finds nothing, serves a placeholder site that hides the mistake.
- **Fly.io's scanners** run framework detection *before* trusting a repository's own Dockerfile, because a Dockerfile
  written for a laptop often does not work on the platform; they refuse when several frameworks match.
- **Render, Railway, DigitalOcean, Koyeb, Dokku, Coolify** all treat "which folder", "which Dockerfile" and "which
  command" as settings on the platform side (root directory, Dockerfile path, build filters, run command), never as
  files they add; Render refuses a deploy when it cannot find the port the app bound.

Two facts settle old questions. Google states that image size does not affect Cloud Run startup (images are streamed);
what matters is import and initialisation time. And Google's own "deploy from source" uses an unpinned `builder:latest`
and Cloud Build, so Fast Deploy's pinned-builder path is stricter than Google's.

### 4.3 The contract outside the repository

Keeping deployment configuration apart from application source is the ordinary GitOps "configuration repository"
pattern, with Argo CD's five stated reasons (separation of concerns, a cleaner audit log, access control, no CI loops,
several apps per source) and Flux's rule that the configuration repository should *point at* the source commit, never
copy it. Binding to an exact commit is a solved primitive (Flux `ref.commit`, Kustomize `?ref=<full sha>`, Docker git
contexts `#<sha>`), and images are bound by digest. Hosted platforms split both ways: Render's Blueprint may live in one
repository and name each service's `repo`, `branch`, root directory, Dockerfile path, health path and pre-deploy command;
Heroku insists on `app.json` in the repository; Railway is retiring its in-repository configuration by 2026-12-01.

**The design that follows.** `apps/<id>/platform.yaml` lives in the platform repository with a `source` block
(`repository`, `commit`); a release is a pull request that moves `commit` and nothing else (what Flux's image automation
does); `reviewed: true` becomes the pull request's approval under the existing CODEOWNERS rule; the contract's own commit
joins the release's chain of identifiers. An in-repository `platform.yaml`, when one exists, is imported once as the
draft of the external one, and one of the two is authoritative per app, recorded in the registry (Railway's "code
overrides dashboard" is the ambiguity to avoid).

**Build inputs from outside.** Docker takes a Dockerfile on standard input with the checkout as context (`docker build
-f- <app>`), or a platform Dockerfile with `--build-context app=<checkout>`; a `<Dockerfile>.dockerignore` beside the
platform's Dockerfile applies; `pack build --path <app> --descriptor <platform project.toml> --env ...` passes the
buildpack inputs; the hash-locked lock can be compiled by the platform into `apps/<id>/` and installed with
`--require-hashes`. So the templates the checker drafts today can be *applied at build time* instead of committed.

**Run-time defaults for what the repository lacks.** Cloud Run's container `command` and `args` override the image's
`ENTRYPOINT` and `CMD`; `PORT`, environment, scaling, timeout, concurrency and the service account are service settings;
a service with no health endpoint still starts under Cloud Run's default TCP startup probe (timeout and period 240 s),
and an HTTP probe accepts any 2xx or 3xx; a job accepts per-execution arguments and environment but not a new command.

**The pipeline in the platform repository, and its price.** GitHub offers no way to run a workflow in another
repository without a file there: reusable workflows need a caller workflow, and required workflows through rulesets are
Enterprise-only. A central pipeline is therefore one `deploy.yml` in the platform repository, started by
`workflow_dispatch` (at most 25 inputs) with the app and commit, checking out the app repository at that commit with a
GitHub App installation token narrowed to that one repository and `contents: read` (one-hour tokens, revoked when the
job ends). Three consequences, each verified against the primary page:

1. *Identity.* The OIDC token then names the platform repository, its ref, its commit and the job's environment; the
   Workload Identity condition moves from "this app's repository" to "the platform repository by id, on `main`, in the
   environment `staging-<app>`". Fast Deploy already pins the environment claim, so this is a change of condition, not of
   mechanism.
2. *Provenance.* GitHub's own provenance (and the SLSA GitHub buildType) names the workflow's repository and commit, that
   is the platform's; other checked-out repositories appear only as optional "additional artifacts". So the platform must
   prove the app commit itself: a custom attestation (`actions/attest` with a `fastdeploy` predicate on public
   repositories, `cosign attest --predicate` with the existing Cloud KMS key on private ones) carrying the app repository,
   its commit, the contract's commit and the hashes of the Dockerfile and lock, following SLSA's split between
   `externalParameters` and `resolvedDependencies`, verified before `gcloud run deploy` and recorded in the release.
3. *Blast radius and minutes.* Today a compromise of one app's workflow reaches only that app's identity; a compromise of
   the platform repository would reach every app's. The platform repository's protection (required review, CODEOWNERS,
   pinned actions, zizmor) becomes the lab's single control point, and the runbook must say so. All deploy minutes bill to
   the platform repository's owner: free while the platform repository is public, as it is.

A fourth consequence is a gift: GitHub's required reviewers and wait timers exist on the Free plan only for public
repositories, and environment secrets in private repositories need a paid plan. The lab's app repositories are mostly
private and its platform repository is public, so environments in the platform repository are also what makes a free
production approval possible for every app (section 5.2).

**Not forks, not mirrors.** A platform-owned copy never syncs itself, runs no workflows and gets no secrets as a fork,
confuses pull-request bases and visibility, and is exactly the "copy instead of pointer" Flux warns against.

### 4.4 Reading a messy repository, and where guessing must stop

The repositories the lab brings are the ones the literature describes: 75.6 percent of Python snippets need non-trivial
configuration and developers guess package names right less than half the time (Gistable, ASE 2018); more than ninety
percent of published notebooks declare no dependencies (ICSE 2021); dependency conflicts come mostly from transitive pins
and overtaken upper bounds (Watchman, ICSE 2020); roughly a third to almost half of GitHub Dockerfiles do not build
(Shipwright ICSE 2021: over a quarter; a 2026 study of 2,000 repositories: only 56 percent produce any image, 2.7 percent
reproducibly), and about ten percent of Dockerized projects are flaky. Automated environment setup has a measured
ceiling: a deterministic script configured 16 percent of EnvBench's single-manifest repositories and the best agent 6.7
percent, while Repo2Run (NeurIPS 2025) reached 86 percent on curated 2024 repositories with tests, and a December 2025
benchmark calls environment construction "the primary bottleneck". The failures are system packages, Python-version
mismatch, timeouts, hardware and undocumented install flags. For the lab this means: a deterministic reader with explicit
precedence and explicit refusals, an LLM only to *draft* for a person, and no promise that every repository deploys.

**Precedence rules the evidence supports** (each borrowed from a platform or a standard named in section 9):

| What | Read in this order | Refuse when |
|---|---|---|
| Python version | the chosen service's Dockerfile `FROM python:X.Y`; the external contract; `.python-version` nearest the service; `runtime.txt` (deprecated form); `Pipfile.lock`; `requires-python`, taking the newest supported version it allows; else the platform default, recorded as a guess | the version is outside 3.11 to 3.15 |
| Dependencies and lock | hashed `requirements*.txt` (installed with `--require-hashes`); `pylock.toml` (PEP 751, Final since 2025-03-31; pip reads it only experimentally since 26.1); `uv.lock` through `uv export` (hashes by default); `poetry.lock` through `uv pip compile --generate-hashes`; `Pipfile.lock` through `pipenv requirements --hash`; the `pip:` section of `environment.yml`; an unlocked manifest compiled once, with the diff shown; dependency groups and extras excluded unless the Dockerfile or the documentation names them; when several manifests coexist, the Compose file's `build.context` says which applies, else Google's order with the ignored files named | conda-only or system packages are needed; no manifest at all (import-based inference is wrong too often) |
| Entrypoint | `Procfile` `web:`; the Dockerfile's `CMD`/`ENTRYPOINT` or Compose `command`; `[tool.fastapi] entrypoint` or a `[project.scripts]` start; Django's `WSGI_APPLICATION`; a module-level `app`/`application` of a known framework in `main.py`, `app.py`, `wsgi.py`, `asgi.py`, `application.py`, `server.py`, `index.py` or `app/__init__.py`; then factories `create_app`/`make_app`; ASGI apps run under uvicorn, WSGI under gunicorn, bound to `0.0.0.0:$PORT`, with the server added to the generated lock when the repository does not declare it | several frameworks or several candidate objects; Django without `WSGI_APPLICATION` |
| Port | Compose `ports` (container side); a single `EXPOSE`; a literal `--port` in the start command; else 8080, always passing `PORT` | — |
| Health | the contract; a Compose `healthcheck`; a literal `/health`-like route in the code; else Cloud Run's TCP startup probe, with the release saying the HTTP probe is off rather than inventing a route | — |
| Configuration and secrets | names from pydantic `BaseSettings` fields (prefix and aliases), `decouple.config('X')` without a default, `environ.Env` schemas and `*_URL` schemes, `os.environ[...]`, Compose `environment` and `env_file` keys, `.env.example`; names only, never values | a secret value is committed (`.env`, keys) |
| Needs | database from drivers, Django `ENGINE` or a `DATABASE_URL` scheme; migrations from `alembic.ini` and `versions/` or Django `migrations/`; cache from a `redis`/`valkey` scheme; queues from celery, rq, dramatiq; a front-end from a `package.json` build step in its own Compose service | — |
| Tests | pytest's own configuration order (`pytest.toml`, `pytest.ini`, `pyproject.toml`, `tox.ini`, `setup.cfg`), `noxfile.py`, `tests/` | none: say "no tests", never fabricate |
| Services in a monorepo | one service per Compose service with a `build`; else one per folder holding its own manifest and entry file, with rebuild filters by path (what Vercel, Railway and Render do); Compose `depends_on` only orders startup | a notebook or a file over 100 MiB as "the app" |

Cloud Run's own Compose deploy (one service with several containers, one instance by default) stays what the 2026-10-14
review said: a way to read the parts, never a deployment unit; its page still says it "isn't a replacement for a
comprehensive infrastructure-as-code strategy for production environments" (read 2026-10-13).

### 4.5 Safety for code nobody has reviewed

Building and running an unknown repository changes the threat, not the architecture. The build is arbitrary code on an
ephemeral GitHub runner with no cloud credentials, which is already the right shape; what the evidence adds, ranked by
risk reduced per effort (all at no idle cost unless said):

1. **A Dockerfile policy gate before any build.** BuildKit runs `RUN` in a sandbox by default and privileged or
   host-network builds need an entitlement the pipeline never grants (`--allow`); the gate refuses `RUN --security`,
   `--network=host`, `ADD` from a URL without `--checksum`, `curl | sh`, disabled TLS or signature checks (Checkov's
   `CKV2_DOCKER_2` to `16`: `curl -k`, `pip --trusted-host`, `--allow-unauthenticated`), `sudo`, and `COPY` of `.git`,
   `.env` or key files; and it requires an explicit non-root `USER`, because a container without one runs as uid 0 on
   Cloud Run (privilege escalation is disabled there, but the benchmarks still want non-root). Trivy's configuration
   scanner or Checkov beside hadolint covers it.
2. **A secret scan of the checkout and of the built image.** Leakage is pervasive (more than 100,000 repositories, NDSS
   2019); GitHub's scanning is free only on public repositories. gitleaks on the tree and TruffleHog on the image, failing
   on any verified hit; a deny-list `.dockerignore` synthesised when the repository has none (`.env*`, `*.pem`, `id_*`,
   `*.key`, `.git`, notebooks, large data); a cap on build-context size. Artifact Analysis now flags secrets in images, but
   after the push and in preview.
3. **No build cache in the release workflow, and `--network none` where the Dockerfile vendors its wheels.** Caches are
   scoped only by branch with client-chosen keys, and SLSA Build L3 forbids a shared cache; the lab's workflows do not cache
   today and must not start.
4. **A vulnerability gate in the industry's wording**: block on fixable critical or high findings and on any "malicious
   package" finding (Artifact Analysis reports those as CRITICAL), on by default for repositories nobody reviewed; and
   re-scan images older than 30 days, because continuous analysis stops after that.
5. **Egress default-deny for unknown apps.** Route `all-traffic` into the VPC with an egress-deny firewall rule keyed on the
   app's service identity and Private Google Access for Google APIs; internet opt-in per app in the contract. Direct VPC
   egress costs nothing at idle and needs no Cloud NAT (a NAT gateway would be about one dollar a month plus data, and can
   add tens of seconds to cold starts). This is the control that turns an unreviewed app from an exfiltration risk into a
   contained one.
6. **The second-generation execution environment, and Cloud Run threat detection for unknown apps.** First generation is
   gVisor (syscall emulation, no protection against hardware side channels), second is a microVM with full Linux (at least
   512 MiB, slower cold start, same price); Cloud Run's runtime threat detectors (reverse shell, credential hunting,
   cryptomining, malicious Python) need Security Command Center Premium at project level and second generation. The
   Billing Catalog prices Premium for Cloud Run at $0.0071 per vCPU-hour, so it is close to nothing for apps that scale to
   zero.
7. **SBOM and provenance attestations on every image** (`--sbom --provenance` in the existing buildx step; cents of
   registry storage), so "are we affected" can be answered without rebuilding.
8. **Binary Authorization requiring the existing Cosign/KMS attestation**, so a bypassed pipeline cannot deploy: the
   Billing Catalog holds no Cloud Run SKU for it (the only one is per GKE cluster), and the policy is checked at every new
   revision; dry-run first. Whether Cloud Run's enforcement reads a Cosign signature directly or needs an attestor is the
   one open point (section 8).
9. **A project per untrusted or data-bearing app.** Google's own guidance calls the project the trust boundary: "services
   within the same project have a default level of trust". Per-app service accounts in one project are right for the lab's
   own apps; an unknown repository, or one that will hold PHI, gets a project of its own (no idle cost; one more Terraform
   root and foundation).
10. **A sensitive-data scan of large data files** before they can enter an image (Sensitive Data Protection: the first
    GiB a month free, then $1 per GiB inspected in storage, $3 per GiB through the content API), gated by size and type.

What the lab should *not* adopt: image debloating (it drops files the app needs; the tool's last release was 2024), and
Cloud Run "sandboxes", which isolate code executed *inside* an app, not the app itself, and are in preview.

### 4.6 Verdict on question 1

The architecture does not change; its inputs move. A repository taken as it is gets: a contract held and reviewed in the
platform repository and bound to its commit; build inputs applied at build time instead of committed; run-time defaults
for what it lacks; a deterministic reader with named refusals; a pipeline that runs from the platform repository and
proves the app commit itself; and, for code nobody reviewed, the ten controls above, of which the first five cost nothing
and change nothing for the lab's own apps. What stays human: the review of the imported contract, secret values, and the
merge that releases. What the lab must accept: some repositories will be refused with a list rather than deployed, and
the platform repository becomes the one place to protect.

## 5. Question 2: production level

### 5.1 What "production" has to mean here

Three different things, which the plan keeps apart because they cost and risk differently:

1. **A production target for the apps**: a second Google Cloud project beside staging, releases promoted into it by
   digest after staging has proved them, with an approval, reliability targets, and the operations around them.
2. **The controller off the laptop**: the thing Claude chat talks to must be always on, reachable, and recoverable
   without the operator's machine.
3. **A tier for protected health information**: what a production that holds PHI must add on Google Cloud (section 5.4).

### 5.2 Delivery and reliability on Cloud Run: what the evidence says

**The research on why production fails.** Of 242 cloud outages with a known root cause across 32 services (SoCC 2016),
upgrades caused 16 percent, network 15, bugs 15, configuration 10 and load 9; 78 percent of the services missed 99.9
percent availability in an average year. Of the catastrophic failures studied at OSDI 2014, 92 percent came from
mishandled errors the software had explicitly signalled, 58 percent were catchable by simple tests of the error-handling
code, and 77 percent reproduce in a unit test. Between 70 and 85 percent of misconfigurations are parameter mistakes, and
up to half are illegal values a checker could refuse (SOSP 2011). Metastable failures (HotOS 2021, OSDI 2022: at least
four of fifteen major AWS outages) are sustained by retries, look-aside caches and slow error paths after the trigger is
gone, and cannot be unit-tested; the mitigations are retry budgets, bounded queues, load shedding and capacity headroom.

**What the practitioners converged on.** Facebook and OANDA (ICSE 2016) found critical issues per deployment "almost
constant regardless of the number of deployments", so more frequent, smaller releases are safer, with a staged rollout to
about one percent first and automatic rollback; Meta's pipelines are 97 percent fully automated (OSDI 2023); Monzo turned
automated rollback on by default across more than 2,100 services using *plain rules* that reuse alert thresholds (an RPC
error rate above 20 percent, panics, database-error spikes), and incidents fell as deployments rose; Google's twenty-year
lessons are "canary all changes", "have a big red button", "recovery mechanisms should be fully tested before an
emergency"; Azure's safe-deployment practice is rings with mandatory bake times, the same for configuration as for code;
Cloudflare, after its 2025-11-18 and 2025-12-05 outages, made configuration changes health-mediated with automatic
rollback by default. Statistical canary analysis (Netflix's Kayenta, archived 2025-12-20) needs at least fifty data points
per metric and hours of traffic, which a lab app never has: the rule-based bake Fast Deploy already runs is the right
instrument, extended from "all traffic at once, then watch" to a real split. DORA's 2025 report finds that higher AI
adoption now raises throughput *and* instability; its countermeasure is small batches and robust automated tests, which is
what the platform's pipeline enforces.

**What Cloud Run offers for it (all verified on pages dated 2026-10-13 or later).** A 99.95 percent monthly SLA per
service; immediate rollback with no health re-check; `--no-traffic --tag` deploys and traffic splits (each percentage step
is a Terraform apply, so the runner keeps doing it); startup, liveness and readiness probes (readiness GA 2026-06-29);
startup CPU boost; a default of 100 maximum instances, which the platform caps lower as a cost safeguard; no native
gradual-rollout feature. Cloud Deploy adds pipelines with required approvals, automated canaries at 25, 50 and 75 percent,
per-phase verification, automatic repair and rollback, and deploy policies for time windows; the first active
multi-target pipeline per billing account is free and each further one $5 a month. It is a sound later option, not a
replacement for the runner the platform already has and has exercised; Skaffold, which it depends on, leaves `gcloud` on
2027-01-15.

**Custom domains.** Google recommends a global external Application Load Balancer; Cloud Run domain mapping is in
Preview, cannot disable TLS 1.0 and 1.1, and "is not recommended for production services"; the `.cloud.run` custom URLs
are in Preview (2026-09-28) without Terraform support. The load balancer's forwarding rule costs $0.025 an hour
($18.25 a month, Billing Catalog 2026-10-16) before data, and Cloud Armor in front of it $5 a month per policy and $1 per
rule; the default `run.app` URL bypasses Cloud Armor unless ingress is restricted to the load balancer. So a custom domain
alone is ninety percent of the lab's monthly cap, and the plan makes it an explicit, per-app choice.

**Databases.** Cloud SQL Enterprise with high availability carries a 99.95 percent SLA and fails over in about a minute,
but shared-core machines are excluded from the SLA and Google says not to use them for production, and single-zone
instances are "recommended only for test and development". The smallest SLA-covered HA shape (1 vCPU, 3.75 GiB) costs
$98.63 a month at list price; an HA `db-f1-micro` $15.33; a single-zone `db-f1-micro` $7.67 plus storage and backups
(about $10.17 with 10 GiB of SSD and backups). Point-in-time recovery gives a recovery point of about five minutes on a
single-zone instance. The plan keeps the micro instance with backups, PITR and deletion protection as production's
default, says in the contract that it has no SLA, and offers the HA shape as a per-app decision with its floor shown.

**GitHub's production controls.** Environments take up to six required reviewers (one approval suffices, self-review can
be prevented), wait timers, branch and tag policies and custom protection rules; the OIDC subject carries the
environment, which Fast Deploy already pins (and its conditions use the numeric repository id and the workflow path, not
the subject, which is why the rename of 2026-10-16 changed nothing). Two facts matter for the plan: required reviewers and
wait timers on the Free plan exist only for *public* repositories, and environment secrets in private repositories need a
paid plan. The central pipeline of section 4.3, whose environments live in the public platform repository, is therefore
also what makes a free production approval possible for every app.

### 5.3 The controller off the laptop

The controller is one Python process (FastAPI, MCP over streamable HTTP, its own OAuth 2.1 server), a few megabytes of
SQLite, a scheduler thread, a read-only cloud identity and a GitHub credential; it must be reachable over public IPv4
HTTPS from Anthropic's range (`160.79.104.0/21`; connectors are IPv4-only), answer OAuth discovery, registration and token
requests within ten seconds, and keep the spec's obligations it already meets (PKCE, hashed and rotated tokens, audience
binding). The MCP specification's current revision (2026-07-28) removes protocol sessions, prefers client ID metadata
documents over dynamic registration and requires issuer validation; Anthropic's connector dialog now recommends "Claude's
published identity" (CIMD). The controller already serves a stateless transport; adding CIMD is a small change.

Three designs were priced from the Billing Catalog (2026-10-16) and the Free Tier page (2026-10-13):

| Design | What it is | Idle floor per month | Why or why not |
|---|---|---|---|
| **A. A free VM** (recommended) | One `e2-micro` in us-central1 (Always Free: the instance, 30 GB of standard disk, 1 GB of egress), Caddy with Let's Encrypt on a lab DNS name, a systemd unit with `Restart=always`, the observer service account attached (no impersonation, no keys), the GitHub App's key in Secret Manager, a Cloud Monitoring uptime check on `/healthz`, Litestream replication of the SQLite file to the backup bucket | **$3.65** (the external IPv4 address, $0.005 an hour; one hour a month free) to $4.04 with Litestream and a Cloud DNS zone; $6.11 more if Google ever ends the free VM (e2-micro list price from the catalog: 0.25 vCPU × $0.021812 + 1 GiB × $0.002924 per hour) | Keeps the process model and the on-disk database untouched; cheaper than ngrok's interstitial-free tier ($10 a month); the VM restarts itself after a host failure and live-migrates for maintenance. | **B. Design A is the plan: the only one that changes nothing in the controller's design, at the lowest floor on Google Cloud.
B stays the fallback if the free VM is withdrawn. The GitHub App (roadmap 7.3, D14) comes with it: installation tokens
live one hour, the private key sits sign-only in Secret Manager, and a fine-grained token tied to one person's account
(30 days by default, at most 366) is the wrong credential for an always-on service. One more reason belongs to section
5.4: a tunnel operated by a third party is in the path of everything the controller says, and nothing the controller says
may ever carry PHI; the free machine removes the third party.

### 5.4 Security and compliance for production

**What any production needs** (each verified on Google's or GitHub's pages; cost at idle in brackets):

- A separate production project with its own state, identities, budget and cap, promoted into by digest [$0]: Google's
  enterprise foundations blueprint puts each environment in its own folder and project and calls nonproduction "a copy
  of production so workloads can be tested before promotion".
- Organization policies [$0, but see the organization below]: Google now enforces seven baseline constraints on every
  organization created on or after 2024-05-03 (no service-account keys, no automatic grants to default service accounts,
  domain-restricted sharing, uniform bucket access); the ones worth adding here are `sql.restrictPublicIp`,
  `storage.publicAccessPrevention`, `run.allowedIngress`, `run.managed.requireInvokerIam`,
  `run.allowedBinaryAuthorizationPolicies`, `gcp.resourceLocations` and `iam.workloadIdentityPoolProviders` pinned to
  GitHub. Every one needs an *organization* resource.
- Audit logs kept where nobody can shorten them [about $0.02 per GB-month]: Admin Activity and System Event logs are
  always written and free for 400 days; a sink of the audit logs to a bucket with a locked retention policy (Bucket
  Lock is irreversible) is what Google's HIPAA guidance asks for and costs storage only.
- Two-step verification with security keys or passkeys on the operator's Google and GitHub accounts [$0]; GitHub has
  required 2FA for contributors since 2023.
- Cloud Run hardening [$0]: the second-generation environment set explicitly, ingress never "all" for production, egress
  controlled, non-root images; Binary Authorization requiring the pipeline's attestation and an organization policy that
  forbids disabling it.
- Backups with a written recovery time and point [storage only]: Cloud SQL automated backups with PITR, Firestore
  scheduled backups (its PITR is off by default and has no free tier), Cloud Storage soft delete (7 days by default) and
  versioning; the restore drill extended to production. Rotation: automatic KMS rotation (symmetric keys), Secret Manager
  rotation schedules.
- An incident procedure for one operator [$0] in the shape of NIST SP 800-61 Rev. 3 (April 2025): detect, mitigate first,
  communicate, review; and the GitHub App instead of a personal token for the platform's own access.
- Supply chain [$0]: the pinned actions, hash-locked dependencies and audit already in place; an SBOM stored beside each
  image; the OpenSSF Scorecard in CI. The provenance Fast Deploy signs today is SLSA Build Level 2 in kind (a hosted
  platform signs); Level 3 would need the signing step isolated from user-defined steps, which the central pipeline of
  section 4.3 can give by putting the signing job behind its own identity.

**What PHI adds.** Google's BAA covers its entire infrastructure and a product list dated 2025-09-17 on which every
service the platform uses or plans sits (Cloud Run, Cloud SQL, Firestore, Secret Manager, Artifact Registry and
Analysis, Pub/Sub, Logging, Monitoring, IAP, Cloud Armor, KMS, Cloud Storage, Scheduler, Sensitive Data Protection,
Security Command Center, VPC Service Controls, Certificate Manager, Load Balancing, Binary Authorization, Assured
Workloads). The agreement is accepted by a click by someone with "full legal authority to bind" the customer and cannot be
modified; HHS certifies no cloud. Google's own rules then apply: never put PHI in an unsupported or pre-GA service, keep
it out of resource names, labels and alert text, export the audit logs. The controls the research marks as required:

- **The organization first.** Assured Workloads' "US Data Boundary for Healthcare and Life Sciences" package is free (it
  admits only services that are BAA-listed, support CMEK and VPC-SC, and stay in the US), VPC Service Controls has no
  separate charge, Security Command Center Standard is free, Access Transparency is on by default for every organization,
  and organization policies are what the name says. All of them need a Google Cloud organization. The lab has one
  (`mail-mboti-org`, id 1029890739128, created 2026-07-27, with the operator's account as its administrator), and the
  staging project is not under it (it has no parent). So Phase 17 begins by creating the production project under the
  organization, where the seven baseline constraints apply automatically because the organization is newer than
  2024-05-03.
- The BAA accepted by someone authorised; the lab's status (covered entity, hybrid entity or business associate) settled
  with the institution; a 60-day breach-notification duty written into the runbook (individuals no later than 60 days
  after discovery; a business associate tells the covered entity within the same limit).
- Data Access audit logs on the data stores (Cloud SQL, Firestore, Cloud Storage, Secret Manager), kept in the locked
  bucket [likely under $5 a month at lab volumes: the first 50 GiB a month are free].
- Customer-managed keys on the data stores and the registry [about $0.06 per key version a month]: not required by
  Google's guidance, which says content is encrypted at rest anyway, but cheap and in the direction of the proposed
  Security Rule update (January 2025: encrypt all ePHI, multi-factor everywhere, restore within 72 hours, an asset
  inventory, controls reviewed every six months; still proposed in July 2026, with a target of July 2027). The platform's
  drills already prove the 72-hour restore; the registry and the Terraform state can print the asset inventory.
- A VPC Service Controls perimeter around the production project, in dry-run mode first, with an access level for the
  pipeline's federated identity; Access Approval switched on.
- **PHI never in the control plane.** The controller's plans, receipts, audit trail and chat summaries carry no
  application data, but `get_recent_logs` returns application log lines, and an application that logs PHI would put it
  through the controller, the tunnel and Claude. For a PHI application the platform must either refuse the logs tool or
  pass the lines through Sensitive Data Protection's de-identification first [the first GiB a month free, then $3 per GiB];
  any third party in that path (today the tunnel) needs its own agreement, which is one more reason for Phase 15.

**Nice to have.** Cloud Run threat detection through SCC Premium at project level [$0.0071 per vCPU-hour, about nothing at
scale-to-zero]; Cloud Armor only where a load balancer exists; a quarterly IAM Recommender review; Artifact Registry
cleanup policies; the OpenSSF badge; and on the MCP side, client ID metadata documents and the stateless 2026-07-28
revision. The platform's design (code decides, plans bound to commits, a person merges, read-only identities, rate limits,
an audit trail, tool descriptions pinned by checksum) already matches the specification's tool guidance ("there SHOULD
always be a human in the loop"), the OWASP agentic and MCP top-ten lists of December 2025, and the published advice on
tool poisoning; nothing in the 2025 papers on MCP threats points at a gap in it beyond the log path above.

### 5.6 Verdict on question 2

Production is three decisions, not one feature. The production target and the controller's machine cost almost nothing
and are the next two phases after "as it is"; the PHI tier is mostly organisational (the organization resource, the
agreement, the lab's status) with cheap technical controls behind it, and it should be planned now so that nothing built
before it has to be undone: the production project created under the organization, Data Access logs and the locked sink
from day one, the logs tool gated for data-bearing apps, and no third party in the control plane.

## 8. Limits of this review

discount" on the page; decided by the first invoice); whether Cloud Run's Binary Authorization consumes Cosign
signatures directly or needs an attestor (the Sigstore integration documented is for GKE); the exact console path for

Cloud Run instances overlap during a rollout, which decides the fallback controller design. Several papers were read from
arXiv versions or abstracts (marked [S] in section 9); the Cito MSR 2017, Koishybayev USENIX 2022 and ARGUS 2023 figures
rest on search snippets. Agent success rates come from benchmarks that do not match the lab's repositories and are given
