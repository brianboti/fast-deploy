# Are we doing it the right way? Lab Deploy 1.8.8 against 2025–2026 research and practice

Written 2026-10-14 as a read-only review. Nothing in the code was changed. The question asked was: apps may have several
containers or different architectures, the platform is not multi-cloud, and it may not yet be easy and trustworthy for
a developer who just wants an app deployed; read what has been built, review the strong 2025–2026 research and current
practice, and say whether the approach is right.

Method: the platform's documents, code, templates and validation records were read (version 1.8.8, commit 498395d;
299 tests pass locally). Six themed literature and practice searches were then run in parallel (platform engineering
and developer experience; multi-cloud and portability; multi-container and multi-architecture; AI agents for operations;
cloud cost; infrastructure-as-code quality, supply chain and safe deployment), each returning only sources it had
fetched or seen in search results. The load-bearing claims were then checked again directly against the primary pages;
section 9 marks each source as fetched, seen only in a search result, or unverified. Two things to keep in mind: the
strongest venues (ICSE, FSE, ASE, EuroSys, NSDI, USENIX Security, NeurIPS, ACM and IEEE journals) are cited where they
exist, but platform engineering as a field has almost no peer-reviewed evidence (a May 2026 review of 88 sources found
two tier-1 papers), so several judgements rest on official vendor documents and industry data; and Google's pricing
pages are script-rendered and could not be read, so the few prices quoted come from secondary pages dated September
2026 and are marked as such.

Acronyms used: IaC (infrastructure as code, Terraform here), MCP (Model Context Protocol, the tool interface Claude
uses), PaaS (platform as a service, Heroku-style hosting), OCI (Open Container Initiative, the standard container image
format), IAP (Identity-Aware Proxy, Google's sign-in gate), SLSA (Supply-chain Levels for Software Artifacts, the build
provenance standard), WIF (Workload Identity Federation, short-lived cloud credentials for GitHub Actions), CNCF (Cloud
Native Computing Foundation), DORA (DevOps Research and Assessment, Google's annual delivery-performance study), SPA
(single-page application, a browser front-end), FinOps (cloud financial operations).

## 1. The short answer

| Concern | Verdict | Why | What to do |
|---|---|---|---|
| Apps with several containers | The one-container-per-service rule is right and is what the vendors themselves recommend. What is missing is support for one *repository* holding several services (back-end, front-end, worker) and a written rule for where caches, queues, workers and front-ends go | Real multi-container apps have a median of two components and are most often app + Postgres (+ Redis + front-end + proxy). Google's new Compose deploy (GA 2026-03-25) folds every Compose service into one Cloud Run service as sidecars with one instance and says it "isn't a replacement for a comprehensive infrastructure-as-code strategy for production environments"; under the request-based billing the platform uses, sidecars get CPU only while a request is being served, so a database, cache or worker as a sidecar is both wrong and not cheaper. Azure's guidance is the same: one app per service | Add apps in subfolders and several `platform.yaml` files per repository; write the component rule (section 4.1); offer Compose only as a way to draft `platform.yaml` |
| Different architectures | Building only `linux/amd64` is correct: Cloud Run "specifically supports the Linux x86_64 ABI format" and no 2025–2026 release note adds arm64. Developers on Apple Silicon run the same image natively at home because the official Python base images are multi-architecture; the GitHub runner builds amd64 natively; nothing in the shipping path emulates | Multi-architecture builds would cost CI time (emulation is reported as 4–10 times slower) and buy nothing at runtime. For ML apps, Cloud Run GPUs are generally available with scale-to-zero but require instance-based billing and at least 4 vCPU and 16 GiB, so they belong in a guarded later option | Keep the rule; add a lint for Dockerfiles; treat a GPU option as a later phase with its own cost guard |
| Not multi-cloud | Right for a one-operator lab on a fixed budget. Keep cheap exits, do not build a second cloud | Deliberate multi-cloud costs more in complexity than it saves (industry and academic consensus); in 2026 most "multi-cloud" is inherited sprawl, not strategy; the research payoff is GPU spot pricing and cross-region storage for AI jobs, not small web apps; measured cross-cloud differences for serverless are modest while billing-model effects inside one cloud are large (up to 4.35 times). The real single-cloud risks are a managed service being retired (AWS App Runner stopped taking new customers on 2026-04-30) and data gravity, and both are answered by a written exit, not by two clouds. No workload-specification standard (Score, Radius, OAM, TOSCA) has a Cloud Run implementation or a peer-reviewed evaluation | Keep the OCI image and Terraform as the portability boundary, keep the generated service close to the Knative-compatible shape Cloud Run's v1 API offers, avoid Terraform 1.14-only features so OpenTofu stays a drop-in, and write and rehearse a one-page exit procedure |
| Not easy and trustworthy yet | Two different problems. *Trust*: the design ("Claude selects reviewed tools, deterministic code decides, a person merges") matches the 2025–2026 consensus on safe agent operation and is stricter than Google's, HashiCorp's and GitHub's own MCP servers. *Ease*: the 2025 PaaS norm is "no Dockerfile needed", Docker builds are a measured friction (about 10 percent of projects have flaky builds, only 56 percent of sampled Dockerfiles build at all), and the contract asks a researcher for about ten files | The remaining trust gaps are legibility, not gates: approvals must be rendered by code from the plan (not summarised by Claude), text read from GitHub must never lead to a write without policy in between, and failures must be loud. For ease, the platform should supply the boilerplate (a repository checker that drafts the missing files, a template Dockerfile, and a trial of Google's Python buildpack as a no-Dockerfile default) and measure onboarding time | Section 4.4 and section 7 |

One sentence: the architecture is right and ahead of common practice; the next work is to make the contract smaller for
developers, let one repository hold several services with a clear rule for the rest, make approvals legible, add
Google's new native spend cap as a second cost layer, and write down the exit and the successor plan.

## 2. Where the platform stands

- Version 1.8.8 on `main` (commit 498395d, 2026-10-14); 299 tests pass; 22 MCP tools, each with safety hints and a
  structured output schema; `docs/VALIDATION.md` records live exercises of every feature.
- Scope: a Python HTTP service, one Dockerfile at the repository root, built on an Ubuntu x64 GitHub runner with
  `docker build --platform linux/amd64`, one container per Cloud Run service, Google Cloud staging in `us-central1`,
  no public endpoints (IAM-authenticated or people through IAP), at most 2 CPUs, 2048 MiB and 3 instances, tests
  required or declared absent, Python 3.11 to 3.15, and `needs` for buckets, topics, Firestore or Cloud SQL Postgres
  and a migration job.
- Three real exercises: the demo app (public repository, Python 3.15), lab-notebook (Postgres with migrations, a
  bucket, a topic and a secret; 24 of 24 live checks; rollback in 53 seconds) and a private copy of the lab's Sophia
  back-end (913 tests, Cosign and Cloud KMS provenance, 10 of 10 live checks).
- Gaps found with Sophia, all confirmed by this review as the right next targets: an app in a subfolder, a Postgres
  reached with a password `DATABASE_URL`, Redis, and front-ends or mobile clients that cannot reach an `authenticated`
  service.
- Already in place and worth saying out loud because the evidence rates them highly: every GitHub Action pinned to a
  full commit SHA, explicit least-privilege `permissions` and `timeout-minutes` on every job, no `pull_request_target`,
  zizmor on every workflow and template in CI, only official actions, WIF identities pinned to branch, workflow file
  and environment with no service-account keys, hash-locked dependencies audited on the app's own Python, signed
  provenance verified before release, branch protection with CODEOWNERS, plan-on-pull-request with a fail-closed
  policy and apply-on-merge, deploy without traffic then probe then switch then probe again with automatic restore,
  and a durable checkpoint with a separate recovery workflow. A 2025–2026 study of 27,863 workflow files found commit
  pinning in 6.3 percent of workflows, no `permissions` block in 71.2 percent and no timeout in 96.3 percent; the
  platform has none of those gaps.

## 3. What the evidence is, and what does not exist

Grades used below: **peer-reviewed** (a published venue), **preprint** (arXiv, not yet reviewed), **official** (vendor
or standards body documentation, authoritative for what a product does), **industry** (surveys and reports, not
reviewed). Things searched for that do not exist as of October 2026, so no one should claim them: a peer-reviewed
evaluation of Score, Radius or the Open Application Model; a 2025–2026 three-way cost study of Cloud Run, Azure
Container Apps and AWS Fargate; a controlled study showing that cost estimates in plans or pull requests change what
developers choose; a 2025 restatement by Google, Meta or Microsoft of the "70 percent of outages come from changes"
figure (it is from the 2016 SRE book); a measured false-positive rate for policy-as-code tools; and a Cloud Run
recommender that sizes CPU or memory (Google's recommender covers only the billing mode, service-account permissions
and secrets in environment variables, so the platform's weekly Monitoring report is the only sizing signal it has).

## 4. Concern by concern

### 4.1 One app, several containers

**What real apps look like.** Two peer-reviewed studies of Docker Compose files give the shape. Across 4,103 GitHub
projects the median application has two components, 26.8 percent use Compose for a single component, the most used
images are Postgres, Redis, Mongo, MySQL and nginx, and Postgres with Redis is the most common pairing (Ibrahim, Sayagh
and Hassan, EMSE 2021). Across 218 self-hosted projects the service types counted were database 365, front-end 343,
back-end 276, cache 111, testing 98, reverse proxy 92, mail 62, object storage 23 and message broker 8; the commonest
patterns are "application with database", "reverse proxy" and "application with database and cache" (Eng, Hindle and
Stroulia, EMSE 2024). Sophia fits exactly: a FastAPI back-end, a front-end, Postgres and Redis. A July 2026 preprint
that asked a frontier model to write Dockerfiles and Compose files for three polyglot repositories found it
consistently omitted how the front-end is served in production and the target build architecture, and concluded those
two facts must be stated in an explicit specification rather than inferred; that is what `platform.yaml` is for.

**What the platforms offer.** Cloud Run runs up to ten containers per instance, one of which receives traffic and the
`PORT` variable; sidecars talk over localhost and start in a declared order with health checks. The decisive sentence
for a cost-first platform is in the sidecar documentation: with the default request-based billing, "sidecars are
allocated CPU in only these scenarios: the instance is processing at least one request; the ingress container is
starting up". A Postgres, Redis or worker sidecar would therefore be throttled between requests, hold data that
disappears with the instance, and force instance-based billing, which removes the scale-to-zero saving. Google's
Compose deployment, generally available since 2026-03-25, maps a whole Compose file to "a single Cloud Run service
with multiple containers", sets "1 maximum instances" by default, turns named volumes into folders in a storage
bucket, accepts images only from Docker Hub and Artifact Registry, and says it "isn't a replacement for a comprehensive
infrastructure-as-code strategy for production environments" while pointing to Terraform. Azure Container Apps
creates one app per Compose service and its documentation says "for most microservice scenarios, the best practice is
to deploy each service as a separate container app". On AWS, App Runner stopped accepting new customers on
2026-04-30, the Copilot CLI reaches end of support on 2026-06-12 and Docker retired its Compose integration for ECS in
2023; "compose to cloud" tooling churns, so a small specification the operator controls is the lower-risk choice.
Cloud Run worker pools (GA 2026-04-14) exist for pull-based background work but, per their documentation, at least one
instance must always run, so they never scale to zero.

**The rule the platform should state** (none of this needs new infrastructure types except the optional cache):

| Component in the app | Where it goes | Why |
|---|---|---|
| Each HTTP-serving component (API, admin UI, a second service) | Its own Cloud Run service with its own `platform.yaml`, possibly in a subfolder of one repository | What Azure recommends; what Cloud Run bills correctly; each scales to zero on its own |
| Postgres, Firestore, files, topics | Managed `needs` (unchanged) | A sidecar database loses its data with the instance |
| Cache or session store | None by default (in-process memory or a Firestore collection); Memorystore for Valkey over Direct VPC egress only with operator approval because it never scales to zero (about 36 to 47 dollars a month for the smallest instance, secondary pricing page, September 2026) | Postgres plus Redis is the commonest pairing, so the contract must answer it explicitly |
| Background worker or queue consumer | Pub/Sub push to a request-billed service, or a Cloud Run job (Cloud Run jobs gained a "delayed execution" preview on 2026-09-08 at reduced pricing) | Worker pools cannot scale to zero |
| Static front-end for lab members | Served by the API container itself behind the same IAP sign-in (zero extra services) | Putting IAP in front of a bucket needs a load balancer with a fixed monthly charge |
| Public front-end | Firebase Hosting (10 GB storage and 10 GB transfer free) calling the API with an IAP programmatic token through a custom OAuth client; Google identities only | Cheapest public static hosting; the API stays authenticated |
| Proxy, logging or telemetry helper, model runner | A sidecar is appropriate | These tolerate CPU throttling between requests |
| Mobile client | IAP programmatic access with an allow-listed OAuth client for Google accounts; non-Google users would need Identity Platform or a public endpoint, which the platform refuses by design | Documented by Google |

**What to add.** (1) `path` or `context` and `dockerfile` in the registry or `platform.yaml` so an app can live in a
subfolder, and several `platform.yaml` files per repository, each its own service (the onboarding tool then creates one
root per service). (2) The table above in `docs/DEVELOPER-CONTRACT.md` with analyzer hints (the analyzer already flags
Redis as "not provided"; it should now say what to do instead). (3) A `compose.yaml` import that drafts `platform.yaml`
files and review questions, never a deployment unit. (4) Later, a `cache: valkey` need behind operator approval with
its cost line in every plan, and a Cloud SQL built-in user with a Secret Manager password as the compatibility path for
apps that only speak `DATABASE_URL` (Google's documentation "strongly recommends" the IAM path, which stays the
default).

### 4.2 Different architectures

**CPU architecture.** The official container contract reads: "Executables in the container image must be compiled for
Linux 64-bit. Cloud Run specifically supports the Linux x86_64 ABI format. If deploying a multi-architecture image, the
manifest list must include linux/amd64." Nothing in the 2025–2026 release notes adds arm64 (Azure Container Apps is
also amd64-only; AWS Fargate is the exception with Graviton). The platform's single `--platform linux/amd64` build on an
x64 runner is therefore the correct and cheapest path, and no emulation happens anywhere in it. Developers on Apple
Silicon are not blocked: the official `python:*-slim` images are multi-architecture, so `docker build` and `docker run`
at home are native arm64, and a pre-flight `docker build --platform linux/amd64` works through Docker Desktop's Rosetta
option. The residual risk, a Python wheel or system package that exists for one architecture only, is caught by the
CI build. If a native arm64 build is ever needed, GitHub now has arm64 runners (free on public repositories since
2025-08-07, private repositories since 2026-01-29 at 0.005 dollars a minute against 0.006 for x64).

**Reproducibility, which is the real architecture risk.** Two 2026 preprints measured Docker builds at scale: of 5,298
images rebuilt from 2023 workflows, 72 percent still built but only four were bit-for-bit identical (Malka, Zacchiroli
and Zimmermann); of 2,000 sampled repositories with a Dockerfile, 56 percent built at all and 2.7 percent reproduced
(Solarin). About 10 percent of 8,132 Dockerized projects show flaky builds that fail with no Dockerfile change (Shabani
and others, UBC, ICSE 2025). The platform's answer, base image by digest, a hash-locked lock file audited on the app's
own Python, and signed provenance that records what was actually built, is what those papers recommend instead of
chasing bit reproducibility. Two cheap additions are supported by the Dockerfile literature: hadolint in the build job
(smells add 4.6 percent to image size on average, up to 89 percent; Durieux, ICSE 2024) and a contract hint to order
layers dependencies-first (a 2025 ISSTA tool cut rebuild time 26.5 percent on average that way).

**GPUs and machine learning.** Cloud Run GPUs (NVIDIA L4) are generally available since 2025-04-07 with scale to zero,
but they require instance-based billing, at least 4 vCPU and 16 GiB, one GPU per instance, and a starter quota of three.
The research says the cost driver is model loading, not container start: cold starts for serverless LLM serving are
dominated by model size (HydraServe, NSDI 2026), and an idle loaded model costs 26 to 66 watts from its CUDA context
alone, so scale-to-zero breaks even after one to five minutes idle (Vadari, 2026 preprint). A guarded `gpu: l4` option
is feasible later: one instance maximum, zonal redundancy off, weights on a read-only bucket volume, the spending cap
able to stop it. It is not a near-term item.

**Other runtimes.** The Dockerfile path is already language-agnostic; only the test and audit steps are Python-specific.
The roadmap's "container-only runtime" item remains the right answer when the first non-Python app appears; nothing in
the evidence argues for building it before then (see "premature abstraction" in 4.4).

### 4.3 Multi-cloud

**What the evidence says.** The cleanest statement of the decision rule is Hohpe's: lock-in is an option whose price is
the switching cost, and paying heavily to remove a risk that is unlikely and cheap to carry is bad economics;
Thoughtworks has held "generic cloud usage" (a home-grown cloud-agnostic layer) on its Hold ring since 2018 because such
layers are "too complex to build and too costly to maintain" and forfeit provider strengths. The 2026 Flexera survey of
753 decision-makers finds multi-cloud rising "often unintentionally" through mergers, siloed teams and inherited
architectures, with wasted spend at 29 percent and rising for the first time in five years. A 2025 HICSS paper frames
multi-cloud as a governance and integration cost; a 2025 mapping of 87 cloud-brokerage papers found 76 assume a single
provider. The Berkeley "Sky computing" line, the strongest academic case for multi-cloud, now targets GPU spot pricing
and cross-region storage for AI jobs (SkyServe, EuroSys 2025; SkyStore, VLDB 2025; SkyNomad, 2026 preprint), which is not
this workload. A 2026 study that deployed one container configuration to Fargate, Cloud Run and Azure Container
Instances found reliability high but configuration semantics the non-portable part (IJCAC 2026); a 2025 EuroSys
benchmark across the three clouds found no single fastest platform; and a 2026 EuroSys study found that billing
practices inside one provider inflate billable resources by up to 4.35 times, so right-sizing on one cloud beats
provider shopping. The two real single-cloud risks are service retirement (App Runner, the AWS analogue of Cloud Run,
closed to new customers on 2026-04-30 after about five years) and data gravity (cross-cloud transfer is far more
expensive than intra-cloud); the EU Data Act abolishes egress switching charges from 2027-01-12 and the three
hyperscalers waived exit egress in 2024, so the financial part of lock-in is shrinking anyway.

**The abstraction landscape, October 2026** (official project pages): Score is a CNCF Sandbox project since July 2024
with no Cloud Run implementation and, by an independent July 2026 assessment, "a compelling concept with a thin
implementation"; Radius is Sandbox, pre-1.0, Azure and AWS only; KubeVela (Open Application Model) is losing
contributors and Kubernetes-bound; Dapr and Crossplane are graduated but need a Kubernetes cluster or an application
SDK; TOSCA 2.0 became an OASIS standard on 2025-09-09 with no serverless orchestrator; two "write once, deploy
anywhere" startups (Winglang, Klotho) shut down within the last 18 months. Knative graduated from CNCF on 2025-10-08, and
Cloud Run's Admin API v1 service definition is compatible with the Knative Serving API, which is the only
standards-based exit Cloud Run offers. OpenTofu is a CNCF Sandbox project since April 2025; Terraform 1.14 has started
to diverge from it.

**Verdict and the cheap hedges.** Single cloud, single region is the right call. Five things keep a second cloud
possible at almost no cost now: the Dockerfile stays the only build artefact and the image stays plain OCI; the
developer-facing `platform.yaml` stays free of Cloud Run-specific fields (the generator maps them); the rendered
service stays close to the Knative-compatible v1 shape; the Terraform avoids 1.14-only features and the platform, not the
app repositories, owns provider bumps (an MSR 2025 study of 13,490 Terraform commits found only 1.2 percent update module
dependencies, with a ten-month lag); and a one-page exit procedure (pull images, export state, export each bucket,
Postgres and Firestore) is written and dry-run once. Revisit only on a concrete trigger: a GPU spot-pricing need, a
grant or data-residency mandate, or a Cloud Run retirement notice.

### 4.4 Easy and trustworthy

**Trust: does the design match the research?** Yes, on every axis the 2025–2026 literature names. The prompt-injection
design patterns paper from Invariant Labs, IBM, ETH, Google, Microsoft and others (June 2025) describes exactly this
shape, an action selector plus plan-then-execute where consequential actions are gated by deterministic policy; CaMeL
(Google DeepMind and ETH, 2025) enforces policy at the tool-call boundary; "Agent Security is a Systems Problem" (May
2026) argues the model must be treated as an untrusted component with invariants in the system; the Berkeley taxonomy of
multi-agent failures (NeurIPS 2025) locates verification failures in system design; a June 2025 study of agents operating
Azure (with Martin Casado and Ang Chen) recommends plans as verifiable programs, organisation rules as formal
specifications checked against plans, escalation of high-stakes actions to humans, least privilege, audit and rollback,
which is the platform's design point by point. The AWS "Agentic AI Security Scoping Matrix" (November 2025) would class
Lab Deploy as Scope 2, prescribed agency with a human approving each consequential action; GitHub's own cloud coding
agent uses the same control points (the agent cannot merge, a person approves workflow runs, the requester is not the
approver). Compared with the official MCP servers, where Google's Cloud Run server can deploy with no confirmation
step, HashiCorp's gates applies behind a flag and GitHub's offers a read-only mode, Lab Deploy is stricter: it has no
apply tool at all; applies happen only in the pipeline after a merge. DORA 2025 (about 5,000 respondents) finds AI
adoption now raises throughput but still lowers delivery stability unless "control systems" exist: automated tests,
mature version control, fast feedback and a high-quality internal platform. That is what this platform is.

**Trust: the three gaps the same literature predicts.**

1. *Approvals must be legible.* Microsoft's AI Red Team reported in June 2026 that human-in-the-loop bypass "was the
   most consistently exploited failure mode, at very high frequency", through consent fatigue and incremental
   escalation, and recommends tiering approvals by reversibility and blast radius and building approval prompts "from
   the underlying tool calls (not from the agent's own description)". OWASP's Agentic Top 10 for 2026 names
   "explainability fabrications" as a live risk and asks for a dry-run diff before approval. A controlled study of 113
   people (August 2026) found standing "ask first" rules blocked 20.1 percentage points less overreach than per-action
   review, which means the lab-deploy-operator skill is a usability aid, not a control; the controls are the policy
   checker, the plan binding and the merge gate. What to change: the infrastructure pull-request comment and the plan
   output should be rendered by code with resources added, changed and destroyed, the monthly floor before and after,
   any exposure change, a reversibility tier, and the chain of identifiers from chat call to plan to run to apply; when
   a second operator exists, the requester should not be the approver.
2. *The read path.* Tool results (build logs, pull-request text, issues) flow back to Claude. Invariant Labs showed in
   May 2025 that an injected GitHub issue made an agent with a broad token leak private data through a public pull
   request; MCPTox (2025) measured tool-poisoning success up to 72.8 percent with refusal rates under 3 percent even for
   strong models. The platform already prevents any read from becoming a cloud write without policy in between; the
   remaining items are to keep the controller's GitHub token scoped to the app repositories, to pin the platform's own
   tool descriptions by hash, and to avoid attaching other MCP servers in the same chat (Anthropic's own connector
   guidance says the same and notes that the Research feature can call connector tools without approval).
3. *Loud failures and explicit targets.* Agents fail silently (a 2026 taxonomy of production incidents), pick
   higher-privilege tools after transient failures (June 2026), and when instructions are underspecified they do not
   fail, they guess: 55.8 to 67.8 percent of runs in a July 2026 benchmark of Claude Code, Codex and OpenCode violated an
   action boundary. The platform's tools already take explicit application identifiers and bind plans to a commit and
   target; keep structured error results and show pipeline failures to the operator directly, cap any retry loop (a
   2026 ESEM study found 13.8 percent of LLM "fixes" to infrastructure code regressed a security rule), and never let
   Claude re-run remediation on its own (AI SRE agents vary by up to 40 points across failure types, SREGym, May 2026;
   ITBench, ICML 2025, saw agents resolve 11.4 percent of SRE scenarios).

**Ease: what the evidence says about the contract.** The 2025 PaaS norm is "no Dockerfile": Heroku's Fir generation
(April 2025) builds with Cloud Native Buildpacks and calls writing production Dockerfiles a complexity to spare
developers, Railway's Railpack (default since September 2025) and Render build from source, and Cloud Run's own source
deploys now read `pyproject.toml` with pip, uv or Poetry (GA 2026-01-13). Fly.io is the exception that requires a
Dockerfile. The Docker-friction numbers in 4.2 explain why. On the research side, a 2025 survey of 527 researchers who
code found their verification of AI-written code "informal and individual" with tests rare, so apps will arrive with
thin tests; a study of 2,396 published bioinformatics web services found 31 percent always reachable and 20.6 percent
never, with hosting location not predicting survival but maintenance did, and its recommendations (containers, pinned
dependencies, version control, HTTPS, a domain, an availability check) are the developer contract almost line for line.
The platform-engineering literature's one firm warning is against "premature abstraction", building elaborate paths
before a real app needs them, and for the "thinnest viable platform" over managed services (CNCF white paper; the May
2026 review); DORA 2024 adds that mandated platforms can cost throughput for a while, so the path must stay an enabler
with an escape hatch. Concretely: the repository checker should *write* the missing files as a draft (template
Dockerfile with a pinned base image, lock file compiled with uv, `requirements-dev.txt`, a health test, `.dockerignore`,
`platform.yaml`) instead of listing them; a trial of Google's Python buildpack inside the existing GitHub build job would
make the Dockerfile optional while keeping the rest of the pipeline (digest, provenance, scan) unchanged; the contract
page should open with the three things a developer must do and push the rest down; and the registry should record
onboarding time and how often the operator had to step in, because most platform teams never measure (industry data) and
cognitive load is the metric the literature asks for.

**The biggest unaddressed risk is the operator, not the stack.** The CNCF maturity model calls a platform run by
temporarily assigned volunteers "Level 1, Provisional" and notes burnout; the NSF science-gateways programme reports
(October 2025) that portals staffed below half a full-time person are the field's typical failure shape and that the
hard step is "the transition from experiment to reliable service"; the HICSS 2025 gateway papers say builders
"underestimate the maintenance resources required". The platform's reproducibility (Terraform, scripts, backups, the
runbook, this document) is therefore its most important sustainability feature. Two cheap steps: a second operator
identity with the runbook rehearsed once, and a quarterly restore drill.

## 5. Cost, which is the lab's first priority

**The design matches the evidence.** Request-based billing and scale to zero are right for bursty low traffic: a 2026
EuroSys study of serverless billing shows wall-clock allocation and keep-alive inflate billable memory by up to 4.35
times on Google's platform, while a 2026 preprint measured a steady microservice load costing 2.4 times more on
serverless than on VMs, so the saving comes precisely from idle time, which these apps have. Google's own guidance says
instance-based billing wins only with a high, steady request rate; from list prices as read on 2026-10-14 (secondary
page), a 1 vCPU, 512 MiB instance is cheaper on instance billing only when busy more than about three quarters of the
time. The "floor and worst-case ceiling" framing matches the academic recommendation for pre-deployment cost estimates
(Columbia and TU Wien, 2024) and the FinOps Foundation's 2026 survey of 1,192 practitioners names "pre-deployment
architecture costing" as the second most requested capability. Google's internal Autopilot work found human-set limits
leave about 46 percent slack against 23 percent for measured limits, which backs the weekly measured report; the one
correction is that Cloud Run's recommender never sizes CPU or memory, so the weekly report is the only sizing signal and
should focus on memory, the main over-billing lever. Whether cost figures in plans change developer behaviour is
unproven in any controlled study; the per-app ceiling that refuses an expensive plan is the control that works
regardless.

**New since the platform was built: Google's native budget spend cap.** Verified on 2026-10-14 from the Cloud Run
release notes and the Cloud Billing documentation: "Budget spend caps" for Cloud Run went to Preview on 2026-07-27 and
to general availability on 2026-10-12. A cap is a budget scoped to one project and one service (Cloud Run, Cloud Run
functions, the Gemini API and the Gemini Enterprise Agent Platform are eligible), monthly only, enforced when gross
estimated usage exceeds 100 percent of the amount. When it trips, "any existing service will fail to serve traffic and
return 5xx errors", jobs fail to start or complete, worker pools stop, in-flight requests finish, nothing is deleted,
and "persistent resources, such as ongoing compute and storage, keep running". It resets on the first of the next month
or is lifted by hand (recovery can take up to an hour; the budget cannot be edited while enforced). It counts gross
list-price cost, so free-tier usage counts toward it, and it ignores VPC connector VMs (the platform uses Direct VPC
egress, which is covered). What this means: the native cap is a simpler, independent backstop for Cloud Run itself, but
it does not stop Cloud SQL, so the platform's own cap workflow (close ingress, stop databases) keeps its job.
Recommendation: create one native cap per project in the console today (a few minutes, no cost) as a second layer,
record it in the runbook with the 5xx behaviour, and keep the workflow.

**Remaining cost risks, in order.** (1) Every cap acts late: budgets publish "multiple times per day" on delayed data
and the native cap "isn't instant"; exposure before any switch trips is bounded by the policy maximum, which the
platform's own ceiling figure already states (about 418 dollars a month at list price for three 2-vCPU, 2-GiB instances
busy all month, our arithmetic), while egress and request fees sit outside it. (2) Fixed floors, not compute, are
where every waste study finds the money (Flexera 29 percent; 83 percent of container spend idle in Datadog's 2024 data;
8 percent CPU utilisation in Cast AI's 2026 Kubernetes telemetry): each Cloud SQL instance (about 8 dollars a month
compute for db-f1-micro plus storage, secondary page), each warm instance (about 10 dollars a month at 1 vCPU and 512
MiB), any Memorystore instance, any worker pool, any serverless VPC connector. Keep minimum instances at zero by
default, as now. (3) Per-event tolls that grow with CI activity: Artifact Analysis charges about 0.26 dollars per new
image digest scanned, which at forty pushes a month exceeds a database; GitHub Actions on private repositories cost
0.006 dollars a minute beyond 2,000 minutes; detailed billing-export queries draw on BigQuery's free quota. These belong
in the cost-hygiene findings if they are not already there.

**Cheapest correct defaults the evidence supports.** Postgres: Cloud SQL db-f1-micro stays the cheapest managed option
on Google Cloud; Firestore's permanent free tier whenever SQL semantics are not needed (as now). Cache: none by default
(section 4.1). Static front-end: from the API container behind IAP, which Google confirmed in March 2026 carries no
charge of its own on Cloud Run and needs no load balancer. Background work: Cloud Run jobs. Never a Kubernetes cluster
(the best 2025 cost-aware autoscaling research gains about a fifth, which does not pay for a control plane).

## 6. Safety and supply chain

**Strongly supported by the evidence and already present.** WIF with pinned subjects and no keys, SHA-pinned
least-privilege workflows and zizmor (the tj-actions/changed-files compromise of March 2025 hit 23,000 repositories
through a repointed tag; a 2026 comparison of nine workflow scanners finds zizmor the only one covering all ten weakness
classes), branch protection with CODEOWNERS (SLSA v1.2, November 2025, added a Source Track that this approximates),
hash-locked dependencies plus audit plus Dependabot (two 2025 papers at FSE and ASE conclude pins alone are not the
control, the lock file is; a 2026 study found 36.7 to 55.7 percent of LLM-written Python tasks name a library version
with a known CVE, which the audit on the lock catches), signed provenance (GitHub's attestations are SLSA Build Level 2;
the Cosign and Cloud KMS path for private repositories is a legitimate equivalent; a USENIX Security 2026 usability study
says identity-based signing is the direction and hand-held keys are the friction point, so keep that path documented),
deterministic templated Terraform rather than model-written (LLM-generated infrastructure code shows 3.2 to 3.9 times
the vulnerability density of human templates in a 2026 benchmark, and syntactic validity is independent of security),
the fail-closed plan policy, and deploy-probe-switch-probe-restore (Google's 2016 figure that about 70 percent of
outages follow a change; Microsoft's 2025 incident study where rollback is the leading mitigation; a 2026 Amazon paper
finding about 5 percent of production commits cause incidents, so a lab shipping weekly should expect a bad deploy every
few months and needs the automatic restore it has).

**Best remaining value for a small lab.** (1) Three or four default post-switch metric checks (5xx ratio, p95
latency, instance restarts over a fixed window from Cloud Run's built-in metrics) wired to the existing restore path:
Meta's 2026 ISSRE paper reports that generic default checks were rarely modified and became the most common check in
production, and that a year of tuning cut false positives from 12.1 to 2.7 percent, which says to start with defaults
and expect to tune. (2) Keep secrets out of Terraform state and plan artifacts (use ephemeral values and write-only
arguments if a password-bearing resource is ever added, keep plan artifacts short-lived, confirm state-bucket IAM and
versioning) and run a scheduled drift plan triaged by severity. (3) Extend the policy checker beyond keys, roles and
public members to encryption at rest and logging, which an EMSE 2025 study of 812 Terraform projects found most
neglected, and keep a few planted-violation plan files as negative tests, because no measured detection rate exists for
policy-as-code tools.

**Can wait, with the reason.** Metric-based canary analysis needs service-level indicators, traffic volume and a year
of tuning; a tagged no-traffic revision is already a free manual canary. SBOMs add little when a hash-locked lock file
is the inventory and downstream SBOM scanners show 92 percent false positives in a 2025 KAUST study. Binary
Authorization re-checks at deploy time what CI already verifies and has no small-team evidence; adopt in dry-run mode
when the time comes. OpenTelemetry has no deployment-safety evidence behind it and Cloud Run's built-in metrics suffice
for default checks. LLM-based deployment verification is research-grade (about 50 percent on drift tasks).

## 8. Limits of this review

The six searches each hit their budget before every planned query ran; the themes most affected were Kubernetes-specific
agent-safety benchmarks, the 2025 Datadog cost report, and a general taxonomy of tool-use errors. Several publisher pages
(ScienceDirect, ACM, Springer, MDPI, Gartner) refused automated reading, so those papers are cited from arXiv versions,
abstracts or search listings and marked accordingly in section 9. Google's pricing pages could not be read; every price
above is from a secondary page dated September 2026 and must be re-read against the official page before any decision
depends on it, as `labdeploy/cost.py` already requires. Three claims that would change a recommendation if wrong were
re-verified directly from the primary page: the Compose mapping and its "not a replacement" sentence, the sidecar
billing rule, and the x86_64 contract; so were the spend-cap behaviour, the App Runner notice, Microsoft's bypass
finding, the Meta false-positive figures, the GitHub Actions compliance figures, the approval-policy study, the
"agents guess" study, the Knative graduation and Cloud Run's recommender scope.
